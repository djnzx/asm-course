## 1. Як ОС запускає програму (~15 хв)

Запуск програми здається тривіальним: надрукував `./program` — і вона запрацювала. Але між натисканням Enter і виконанням першої інструкції `main` відбувається складна послідовність дій, розподілена між оболонкою, ядром, динамічним лінкером і стандартною бібліотекою. Розуміння цього ланцюжка пояснює, чому `main` — не перша інструкція програми, як ОС ізолює процеси один від одного, і що саме відбувається після повернення з `main`.

### Крок 1. Shell і fork/exec

Коли оболонка (bash, zsh або будь-яка інша) отримує команду `./program`, вона не "перетворюється" на нову програму. Вона викликає системний виклик `fork()`, який створює точну копію поточного процесу — копіюється адресний простір, файлові дескриптори, стан регістрів. Новий процес (дочірній) відразу викликає `execve("/path/to/program", argv, envp)`. Саме `execve` є ключовим: він замінює образ поточного процесу на вміст зазначеного файлу. Після успішного `execve` від дочірнього процесу оболонки не залишається нічого — тільки нова програма з тим самим PID.

Ця модель `fork + exec` — фундаментальна для Unix. Вона пояснює, чому дочірній процес успадковує відкриті файли від батька, чому можна перенаправляти stdin/stdout до `exec`, і чому сигнали мають своїх власників.

### Крок 2. Ядро читає ELF-заголовок

Ядро отримує керування після `execve` і першим ділом дивиться на перші байти файлу — **магічне число** (`magic bytes`). Для ELF це чотири байти: `0x7F`, `E`, `L`, `F`. Вони ідентифікують формат. Ядро підтримує декілька форматів (`binfmt`): ELF, скрипти з `#!`, а через `binfmt_misc` — навіть Windows PE-файли через Wine.

Для ELF ядро читає **ELF header** — структуру на початку файлу, яка описує: архітектуру (`e_machine`: x86-64, ARM тощо), тип файлу (виконуваний, бібліотека, об'єктний), адресу точки входу (`e_entry`), зміщення таблиці **program headers** (`e_phoff`) та їх кількість.

Program headers описують сегменти — неперервні області файлу, що мають потрапити у пам'ять. Найважливіші типи:

- `PT_LOAD` — сегмент, який треба відобразити у пам'ять. Типова програма має два: один для коду (read + execute), один для даних (read + write).
- `PT_INTERP` — шлях до динамічного лінкера, наприклад `/lib64/ld-linux-x86-64.so.2`. Його наявність означає, що програма динамічно скомпонована.
- `PT_PHDR` — адреса, де у пам'яті знаходиться сама таблиця program headers.

### Крок 3. Відображення у віртуальну пам'ять

Ядро не копіює файл у RAM — воно створює **відображення** (`mmap`). Для кожного `PT_LOAD` сегменту ядро викликає `mmap` і прив'язує діапазон віртуальних адрес до відповідної частини файлу. Сторінки завантажуються у RAM ліниво — лише тоді, коли процесор до них звертається (page fault).

Адресний простір процесу після цього виглядає так (зверху — старші адреси):

```
0xFFFFFFFFFFFFFFFF
  [недоступна область ядра]
  [стек]          ← росте донизу; тут argc, argv, envp, допоміжний вектор (auxv)
  [ld.so]         ← якщо є динамічне компонування
  [libc.so, ...]  ← відображені бібліотеки
  [heap]          ← росте догори; керується через brk/mmap
  [.bss]          ← неініціалізовані глобальні дані (нулі)
  [.data]         ← ініціалізовані глобальні дані
  [.text]         ← код програми
0x0000000000400000 (типова базова адреса для не-PIE)
```

Для **PIE** (Position Independent Executable) ядро обирає базову адресу випадково — це **ASLR** (Address Space Layout Randomization). Зловмисник не може наперед знати, де знаходиться код або стек, що ускладнює атаки типу return-to-libc.

### Крок 4. Динамічний лінкер

Якщо у файлі є сегмент `PT_INTERP`, ядро відображає у пам'ять ще й динамічний лінкер (`ld.so`) і передає йому керування — не програмі. `ld.so` стає фактично першим кодом, який виконується від імені нового процесу.

Динамічний лінкер виконує такі кроки:

1. Читає таблицю `DT_NEEDED` з ELF — список бібліотек (`libc.so.6`, `libpthread.so.0` тощо).
2. Знаходить ці бібліотеки у стандартних каталогах (`/lib`, `/usr/lib`, шляхи з `LD_LIBRARY_PATH`, кеш `/etc/ld.so.cache`).
3. Відображає кожну бібліотеку у адресний простір процесу.
4. **Вирішує символи**: заповнює таблицю `PLT/GOT` — зв'язує виклики типу `printf@plt` із реальними адресами функцій у `libc.so`.
5. Передає керування на адресу `e_entry` виконуваного файлу — тобто на `_start`.

Саме тому змінна оточення `LD_PRELOAD` дозволяє підмінити функції з `libc` — `ld.so` завантажує вказану бібліотеку першою, і при вирішенні символів знаходить підмінені функції раніше оригінальних.

### Крок 5. _start і __libc_start_main

Точка входу `e_entry` вказує не на `main`, а на функцію `_start`, яка надходить з файлу `crt0.o` (C runtime). Цей файл автоматично додає лінкер при збірці будь-якої C-програми.

Перш ніж дивитись на код `_start`, варто визначити поняття **ABI** (Application Binary Interface) — набір угод, що визначають як саме на рівні машинного коду взаємодіють між собою компоненти: у яких регістрах передаються аргументи, хто зберігає яких регістри, як вирівнюється стек, яким чином повертаються значення. ABI — це те саме для бінарного коду, що й API для вихідного: якщо два компоненти дотримуються одного ABI, вони можуть взаємодіяти навіть якщо скомпільовані різними компіляторами або написані різними мовами. На Linux x86-64 стандартом є **System V AMD64 ABI** — він визначає calling convention для звичайних функцій. `_start` написана на асемблері і виглядає приблизно так:

```nasm
_start:
    xor     rbp, rbp           ; обнулення rbp — frame pointer (POSIX ABI вимога)
    pop     rdi                ; argc — лежить на стеку (не через регістри!)
    mov     rsi, rsp           ; argv — вказівник на масив рядків
    and     rsp, ~0xF          ; вирівнювання стека до 16 байт
    call    __libc_start_main
```

Зверніть увагу: при запуску `_start` не отримує аргументи через регістри (як звичайна функція) — вони вже лежать на стеку, покладені ядром перед передачею керування.

`__libc_start_main` — функція у `libc`, яка виконує фінальну ініціалізацію:

- Реєструє `__cxa_atexit` — функцію, яку буде викликано при завершенні.
- Запускає **конструктори глобальних об'єктів** — функції зі списку `.init_array`. У C++ це конструктори статичних об'єктів; у C — функції з атрибутом `__attribute__((constructor))`.
- Викликає `main(argc, argv, envp)`.
- Після повернення з `main` — запускає деструктори (`atexit`-функції, список `.fini_array`).
- Викликає системний виклик `exit` з кодом, який повернув `main`.

### Чому це важливо

Знання цього ланцюжка відповідає на практичні питання:

**Чому не можна просто "стрибнути на `main`" зовнішнім кодом?** Бо стек у цей момент не вирівняний, `argc`/`argv` не підготовлені, глобальні конструктори не викликані, і `stdio` не ініціалізовано. Програма впаде або поведеться непередбачувано.

**Чому `LD_PRELOAD` дозволяє замінити `malloc`?** Бо динамічний лінкер вирішує символи зліва направо у порядку завантажених бібліотек, і бібліотека з `LD_PRELOAD` завантажується першою. Знайшовши символ `malloc` у ній, лінкер більше не шукає далі.

**Чому статично скомпоновані програми запускаються трохи швидше?** Бо відсутній крок роботи `ld.so` — не треба знаходити і відображати бібліотеки, не треба вирішувати символи. Для коротко живучих утиліт (як `busybox`) це суттєво.

**Чому `_exit()` відрізняється від `exit()`?** `exit()` з `libc` перед завершенням скидає буфери `stdio`, викликає функції зареєстровані через `atexit`, і запускає деструктори `.fini_array`. `_exit()` — це прямий системний виклик `exit_group`, який нічого з цього не робить. Якщо `_exit` викликати посеред роботи `stdio`, незаписані дані загубляться.

**Чому в наступних розділах можна написати програму без `libc`?** Бо ядро не знає нічого про `libc`. Воно вимагає лише коректного ELF-файлу з хоча б одним `PT_LOAD` сегментом і валідною адресою `e_entry`. Все, що `libc` робить до `main` і після нього — це зручна обгортка, а не обов'язкова умова.

## 2. System calls (~15 хв)

Програма у просторі користувача існує в ізольованому середовищі. Вона не може напряму звернутись до диска, мережевої карти, екрана чи будь-якого іншого пристрою. Будь-яка спроба звернутись до привілейованого ресурсу напряму призведе до виключення захисту і завершення процесу. Єдиний легальний спосіб взаємодіяти зі світом — попросити ядро через **системний виклик** (syscall).

### Кільця привілеїв

x86-64 підтримує чотири рівні привілеїв — **кільця** (rings) від 0 до 3. Ядро ОС виконується у ring 0 (найбільше привілеїв), код користувача — у ring 3 (найменше). Ring 1 і Ring 2 сучасними ОС не використовуються. Різниця між кільцями принципова: у ring 0 доступні всі інструкції процесора, у ring 3 — тільки безпечне підмножина. Інструкції на кшталт `hlt`, `in`/`out`, запис у `CR0`/`CR4`, зміна таблиць сторінок — все це заборонено у ring 3. Спроба виконати таку інструкцію генерує виключення `#GP` (General Protection Fault), і ядро завершує процес.

Системний виклик — це контрольований перехід із ring 3 у ring 0. Контрольований означає: процесор перевіряє спеціальну таблицю (MSR `LSTAR` на x86-64) і стрибає строго на зареєстровану ядром точку входу. Довільно "зістрибнути" у ядро не можна — це захист від escalation атак.

### Механізм syscall на x86-64

На сучасному x86-64 Linux системний виклик виконується інструкцією `syscall`. Виклик підпорядковується власному **ABI** — не System V AMD64 ABI, яким користуються звичайні функції:

| Роль               | Syscall ABI  | Функціональний ABI |
|--------------------|--------------|--------------------|
| Номер / повернення | `rax`        | —                  |
| Аргумент 1         | `rdi`        | `rdi`              |
| Аргумент 2         | `rsi`        | `rsi`              |
| Аргумент 3         | `rdx`        | `rdx`              |
| Аргумент 4         | **`r10`**    | `rcx` ← різниця!   |
| Аргумент 5         | `r8`         | `r8`               |
| Аргумент 6         | `r9`         | `r9`               |
| Зіпсовані          | `rcx`, `r11` | залежить від ABI   |

Четвертий аргумент — ключова відмінність: `r10` замість `rcx`. Причина технічна: інструкція `syscall` сама записує адресу повернення у `rcx` і поточний `rflags` у `r11`, тому ядро не може їх використати для аргументів.

### Три приклади системних викликів

**`write` — вивести рядок:**

```nasm
section .data
    msg db "Hello, World!", 10   ; рядок + newline
    len equ $ - msg

section .text
global _start
_start:
    mov  rax, 1       ; syscall №1 = write
    mov  rdi, 1       ; fd = 1 (stdout)
    mov  rsi, msg     ; адреса буфера
    mov  rdx, len     ; довжина
    syscall
```

**`exit` — завершити процес:**

```nasm
    mov  rax, 60      ; syscall №60 = exit
    xor  rdi, rdi     ; код завершення = 0
    syscall
```

**`read` — прочитати з stdin:**

```nasm
    mov  rax, 0       ; syscall №0 = read
    xor  rdi, rdi     ; fd = 0 (stdin)
    mov  rsi, buf     ; куди читати
    mov  rdx, 256     ; скільки байт максимум
    syscall
    ; після syscall: rax = кількість прочитаних байт, або від'ємне = errno
```

### Таблиця номерів системних викликів

Кожен системний виклик має унікальний числовий номер. Ці номери фіксовані для конкретної архітектури і версії ядра — вони є частиною стабільного ABI Linux (ядро гарантує їх незмінність). Найпоширеніші виклики на x86-64:

| №   | Назва        | Опис                                      |
|-----|--------------|-------------------------------------------|
| 0   | `read`       | читання з файлового дескриптора           |
| 1   | `write`      | запис у файловий дескриптор               |
| 2   | `open`       | відкрити файл                             |
| 3   | `close`      | закрити дескриптор                        |
| 9   | `mmap`       | відобразити пам'ять / файл                |
| 11  | `munmap`     | зняти відображення                        |
| 12  | `brk`        | розширити heap                            |
| 39  | `getpid`     | отримати PID процесу                      |
| 57  | `fork`       | створити дочірній процес                  |
| 59  | `execve`     | замінити образ процесу                    |
| 60  | `exit`       | завершити поточний потік                  |
| 231 | `exit_group` | завершити весь процес (усі потоки)        |

Повна таблиця міститься у заголовковому файлі ядра `arch/x86/entry/syscalls/syscall_64.tbl`. На інших архітектурах (ARM, RISC-V, MIPS) номери відрізняються — код із жорстко закодованим `60` для `exit` не працюватиме на ARM.

### Коди помилок

Якщо системний виклик завершується помилкою, `rax` містить від'ємне значення у діапазоні від `-1` до `-4095`. Це від'ємний код `errno` — наприклад, `-2` означає `ENOENT` (файл не знайдено), `-13` — `EACCES` (доступ заборонено). Функції `libc` (такі як `open`, `read`, `write`) перевіряють цей діапазон, при від'ємному значенні записують `|rax|` у глобальну змінну `errno` і повертають `-1`. При прямому використанні `syscall` перевірку на помилку треба виконувати самостійно.

### strace: підглядання за системними викликами

Утиліта `strace` дозволяє побачити всі системні виклики, які виконує програма, у реальному часі:

```bash
strace ./program
```

Виведення показує назву виклику, аргументи і результат. Наприклад:

```
execve("./program", ["./program"], 0x... /* 42 vars */) = 0
write(1, "Hello, World!\n", 14)         = 14
exit_group(0)                           = ?
```

`strace` корисний для розуміння що насправді робить програма: скільки разів вона звертається до диска, яких файлів відкриває, де блокується на `read`. Для діагностики продуктивності — `strace -c` виводить зведену статистику кількості і часу викликів. Розуміння системних викликів на рівні ASM робить результати `strace` повністю зрозумілими без додаткових пояснень.

### vDSO: системний виклик без переходу у ядро

Перехід з ring 3 у ring 0 і назад коштує кількасот тактів процесора. Для деяких часто викликаних операцій (насамперед `gettimeofday`, `clock_gettime`) ядро використовує трюк під назвою **vDSO** (Virtual Dynamic Shared Object). Ядро відображає у адресний простір кожного процесу невелику бібліотеку із реалізацією цих функцій прямо у ring 3 — вони читають дані з розділюваної сторінки пам'яті, яку ядро постійно оновлює, і повертають результат без жодного переходу у ядро. `libc` автоматично використовує vDSO: виклик `clock_gettime()` з коду на C може взагалі не виконувати `syscall`.

### Повна програма без libc

Маючи `_start`, `write` і `exit`, можна зібрати повноцінний виконуваний ELF без жодного зв'язку з `libc`:

```bash
nasm -f elf64 program.asm -o program.o
ld program.o -o program        # лінкується без -lc
./program
echo $?                        # код завершення
```

Такий бінарник займає кілька сотень байт, не має динамічних залежностей (`ldd` покаже "not a dynamic executable") і запускається навіть у мінімальному контейнері без встановленого libc. Саме так влаштовані деякі утиліти у initramfs і мінімальні Docker-образи.

## 3. Режими процесора (~15 хв)

Коли сучасний x86-64 процесор вмикається, він не одразу опиняється у тому 64-бітному середовищі, яке знайоме програмісту. Він проходить через кілька режимів роботи — і кожен наступний режим потребує явної підготовки та перемикання у машинному коді. Без цього ланцюжка жодна сучасна ОС не запустилась би.

### Real mode

Процесор стартує у **real mode** — 16-бітному режимі, який є прямим спадкоємцем архітектури Intel 8086 (1978 рік). У цьому режимі:

- Адресний простір — лише **1 МБ** (20-бітна шина адреси).
- Адресація — сегментна: фізична адреса = `сегмент × 16 + зміщення`. Наприклад, `CS:IP = 0xF000:0xFFF0` дає фізичну адресу `0xFFFF0`.
- Немає захисту пам'яті — будь-яка програма може записати у будь-яку адресу, включно з таблицями переривань і кодом BIOS.
- Немає привілеїв — весь код виконується з повним доступом до апаратури.
- Набір інструкцій — 16-бітний: регістри `ax`, `bx`, `cx`... (а не `eax`, `rax`).

Саме у real mode BIOS виконує POST (Power-On Self Test), ініціалізує пристрої і зрештою завантажує перший сектор (MBR) з диска за адресою `0x7C00`. Туди передається керування — і завантажувач, що там знаходиться, починає роботу теж у real mode.

У real mode переривання обслуговуються через **IVT** (Interrupt Vector Table) — таблицю з 256 чотирибайтових записів на початку пам'яті (`0x0000:0x0000`). Кожен запис — це адреса обробника у форматі `сегмент:зміщення`. BIOS заповнює цю таблицю обробниками для стандартних сервісів: `int 0x10` (відеовиведення), `int 0x13` (диск), `int 0x16` (клавіатура). Завантажувач може використовувати ці сервіси до перемикання в protected mode, після чого вони стають недоступними.

### Protected mode

Щоб отримати захист пам'яті і більший адресний простір, завантажувач перемикає процесор у **protected mode** (32 біти). Кроки перемикання фіксовані специфікацією:

1. Підготувати **GDT** (Global Descriptor Table) — таблицю, яка описує сегменти пам'яті: їх базу, розмір і права доступу (код/дані, ring 0/ring 3). Кожен запис у GDT — 8-байтовий **дескриптор сегменту**, де закодовані базова адреса, ліміт і поле прав (`Present`, `DPL` — рівень привілеїв, тип — код чи дані, `Granularity` — чи ліміт у байтах чи у сторінках 4 КБ). Мінімально для завантажувача потрібні три дескриптори: нульовий (обов'язковий за специфікацією), код ring 0 і дані ring 0.
2. Завантажити адресу GDT у регістр `GDTR` інструкцією `lgdt`.
3. Встановити біт `PE` (Protection Enable) у регістрі `CR0`:
   ```nasm
   mov eax, cr0
   or  eax, 1
   mov cr0, eax
   ```
4. Виконати **far jump** (`jmp cs_selector:label`) — це примушує процесор завантажити новий дескриптор сегменту коду з GDT і повністю переключитись у protected mode.

У protected mode адресний простір розширюється до **4 ГБ** (32-бітні регістри). З'являються привілеї (ring 0–3) і апаратна ізоляція пам'яті через дескриптори сегментів. Переривання у protected mode обслуговуються через **IDT** (Interrupt Descriptor Table) замість IVT — кожен запис у ній описує обробник разом із його привілейованим рівнем. Сучасні ОС використовують protected mode лише транзитно — щоб потрапити у long mode.

### Long mode

**Long mode** (він же IA-32e mode) — 64-бітний режим, у якому виконується весь сучасний код. Перемикання з protected mode у long mode вимагає додаткових кроків:

1. Підготувати початкові **сторінкові таблиці** (PML4 → PDPT → PD → PT) — щонайменше відобразити ті адреси, де знаходиться сам завантажувач.
2. Завантажити фізичну адресу PML4 у регістр `CR3`.
3. Встановити біт `PAE` (Physical Address Extension) у `CR4`:
   ```nasm
   mov eax, cr4
   or  eax, (1 << 5)   ; PAE bit
   mov cr4, eax
   ```
4. Встановити біт `LME` (Long Mode Enable) у MSR `EFER` (`0xC0000080`):
   ```nasm
   mov ecx, 0xC0000080
   rdmsr
   or  eax, (1 << 8)   ; LME bit
   wrmsr
   ```
5. Увімкнути сторінкування — встановити біт `PG` у `CR0` (одночасно з `PE`).
6. Виконати far jump на 64-бітний дескриптор коду у GDT.

Після цього процесор переходить у **64-bit submode** long mode: доступні `rax`, `rbx`, ... `r15`, 64-бітна адресація, і всі механізми, описані у попередніх лекціях.

Варто також знати про **System Management Mode** (SMM) — окремий «прихований» режим процесора з найвищим рівнем привілеїв, у який процесор перемикається по апаратному сигналу SMI (System Management Interrupt). У SMM виконується код з прошивки (BIOS/UEFI), недоступний ОС і невидимий для неї. SMM використовується для управління живленням, термічного захисту, емуляції застарілого обладнання. Для системного програміста важливо знати: SMM існує, ОС його не контролює, і затримки від SMI можуть непередбачувано впливати на системи реального часу.

У long mode сегментація фактично вимкнена — всі сегменти мають базу 0 і ліміт `0xFFFFFFFFFFFFFFFF`, тобто покривають весь адресний простір. Захист пам'яті тепер цілком сторінковий (через CR3 і таблиці сторінок). Одна важлива деталь — **canonical addresses**: у 64-бітному режимі валідні адреси мусять мати біти 48–63 рівними біту 47 (знакове розширення). Адреси від `0x0000000000000000` до `0x00007FFFFFFFFFFF` — user space; від `0xFFFF800000000000` до `0xFFFFFFFFFFFFFFFF` — kernel space. Все що між — «non-canonical» і спричиняє `#GP` при спробі звернення.

### Порівняння режимів

| Характеристика      | Real mode  | Protected mode | Long mode  |
|---------------------|------------|----------------|------------|
| Розрядність         | 16 біт     | 32 біти        | 64 біти    |
| Адресний простір    | 1 МБ       | 4 ГБ           | 128 ТБ     |
| Захист пам'яті      | Немає      | Сегментний     | Сторінковий|
| Привілеї (rings)    | Немає      | Є              | Є          |
| Віртуальні адреси   | Немає      | Є              | Є          |
| Коли використовують | BIOS, MBR  | Транзитно      | ОС, програми|

### UEFI і новий шлях завантаження

Сучасні машини зазвичай використовують **UEFI** замість BIOS. UEFI запускає завантажувач вже у protected mode (або навіть у спеціальному «UEFI long mode» на деяких реалізаціях), тому класичний 16-бітний real mode можна взагалі не бачити. Проте архітектурно ланцюжок залишається подібним: є firmware (UEFI замість BIOS), є завантажувач (GRUB/systemd-boot у вигляді `.efi`-файлу), і є ядро, яке отримує повністю налаштоване 64-бітне оточення. Знання режимів все одно необхідне при розробці власного UEFI-додатку або при аналізі проблем з ланцюжком завантаження.

### Чому це важливо

Написання будь-якого завантажувача — чи то GRUB, чи власний мінімальний bootloader — вимагає пройти весь цей шлях: стартувати у real mode, виконати перемикання через protected mode у long mode, і лише тоді передати керування ядру. Розуміння режимів пояснює, чому 16-бітні обробники BIOS (`int 0x10`, `int 0x13`) недоступні з long mode і вимагають або повернення у real mode, або UEFI-аналогів. Воно також пояснює, чому помилка у сторінкових таблицях при перемиканні призводить до миттєвого зависання без жодного повідомлення — процесор просто не знає, куди стрибнути після виключення. Налагодження завантаження без знання цих режимів рівнозначне роботі наосліп.

## 4. Bare metal: що відбувається при увімкненні (~15 хв)

Запуск програми під ОС — це комфортне середовище: пам'ять відображена, стек підготовлений, бібліотеки завантажені. На bare metal нічого з цього немає. Процесор вмикається у стані, де навіть поняття «стек» ще не існує — і перший код мусить створити цей фундамент з нічого.

### Reset vector: перша інструкція після живлення

Коли на процесор подається живлення або надходить сигнал RESET, апаратура встановлює регістри у відомий початковий стан і починає виконання з **reset vector** — фіксованої адреси, жорстко закодованої у специфікації процесора.

На **x86**: після RESET регістр `CS` отримує значення `0xF000`, а `IP` — `0xFFF0`. Це дає фізичну адресу `0xFFFF0` у real mode. За цією адресою — кінець адресного простору 1 МБ, там у ПЗП знаходиться код BIOS. Перша інструкція зазвичай — `jmp far` на початок основного коду BIOS. На сучасних машинах із UEFI адресу `0xFFFFFFF0` відображено на мікросхему SPI Flash із прошивкою.

На **ARM Cortex-M**: reset vector влаштований інакше. Перші два 32-бітних слова у Flash (за адресою `0x00000000`) — це не інструкції, а дані: початкове значення стека (`sp`) і адреса **reset handler**. Процесор при старті апаратно читає ці два слова, завантажує `sp` і виконує перехід на reset handler. Це означає, що стек на ARM Cortex-M готовий ще до першої інструкції коду — принципова відмінність від x86. Далі у Flash іде **таблиця векторів переривань** (Vector Table): кожен запис — 32-бітна адреса обробника відповідного переривання або виключення. Якщо таблиця некоректна або відсутня у потрібному місці, перше ж переривання спричинить HardFault.

### Стан процесора після RESET

Незалежно від архітектури, стан після RESET є мінімальним і суворо визначеним специфікацією:

- Більшість регістрів загального призначення — **невизначені** (містять довільні значення).
- Кеші, TLB, передбачувач переходів — **очищені** або у невизначеному стані.
- Переривання — **вимкнені** (апаратно).
- Периферійні пристрої — у стані RESET; тактова частота може бути мінімальною (внутрішній RC-генератор замість зовнішнього кварцу).
- На x86: сегментні регістри і режим — real mode; на ARM: залежить від конфігурації виводів процесора.

Важливий наслідок: **стека немає**. Жодна C-функція не може бути викликана до того, як буде налаштовано `sp`. Якщо спробувати — `push`/`pop` у функції запишуть або прочитають дані за невідомою адресою, і найімовірніший результат — апаратне виключення або тихе пошкодження пам'яті. З цієї ж причини ніяких локальних масивів великого розміру у startup-коді бути не може — вони теж вимагають стека.

Ще одна неочевидна деталь: одразу після RESET на багатьох мікроконтролерах тактова частота ядра — мінімальна. Наприклад, STM32 стартує на внутрішньому RC-генераторі 8 або 16 МГц замість штатних 72–168 МГц. Якщо код відразу налаштовує UART на 115200 baud, але PLL ще не увімкнений, швидкість буде неправильною. Тому ініціалізація тактування — перший крок після встановлення стека, ще до будь-якої периферії.

### Карта пам'яті на bare metal

На відміну від програми під ОС, де карту пам'яті готує ядро, на bare metal її треба знати наперед і описати у linker script. Типова карта для ARM Cortex-M мікроконтролера (наприклад, STM32):

```
0x00000000  Flash (код + константи + вектори) — тільки читання
0x20000000  RAM (стек, .data, .bss, heap)     — читання і запис
0x40000000  Peripheral registers               — регістри периферії
0xE0000000  System control (NVIC, SysTick...) — системні регістри ядра
```

Звернення до невідображеної адреси генерує апаратне виключення **HardFault** (на ARM) або `#PF` / `#GP` (на x86 у protected mode). На мікроконтролері без ОС HardFault — це зазвичай зависання: обробник за замовчуванням — нескінченний цикл. Для дебагу корисно підключити JTAG/SWD і подивитись вміст регістрів `LR`, `PC` і стекового фрейму, які ARM Cortex-M автоматично зберігає перед входом у обробник виключення — за ними можна точно визначити, яка інструкція спричинила HardFault і яким було значення покажчика стека у той момент.

### Що мусить зробити перший код

Порядок ініціалізації на bare metal є строгим — порушення порядку призводить до непередбачуваної поведінки:

1. **Налаштувати тактування** — перемкнути на зовнішній кварц або PLL, щоб отримати потрібну частоту. На x86 цим займається BIOS; на мікроконтролері — startup-код або `SystemInit()`.
2. **Встановити стек** — записати коректну адресу у `sp` (ARM) або виконати `mov esp, stack_top` (x86). До цього моменту — жодних викликів функцій.
3. **Скопіювати `.data` з Flash у RAM** — ініціалізовані глобальні змінні зберігаються у Flash як константи, але мають бути у RAM для можливості запису. Startup-код копіює їх у потрібне місце.
4. **Заповнити `.bss` нулями** — неініціалізовані глобальні змінні за стандартом C мусять бути нулями. У Flash ніяких нулів немає — їх треба записати у RAM явно.
5. **Ініціалізувати периферію** — налаштувати необхідні порти, UART, таймери до того, як логіка програми почне їх використовувати. На деяких мікроконтролерах тактування периферії за замовчуванням вимкнене — звернення до регістра неактивної периферії просто ігнорується або спричиняє HardFault.
6. **Викликати `main()`** — лише тепер оточення достатньо підготовлене. Якщо `main` раптово повертає значення (що не мало б відбуватись на bare metal), startup-код зазвичай кидає процесор у нескінченний цикл, бо нікуди більше повертатись.

### Порівняння: ОС vs bare metal

| Аспект                   | Під ОС                          | Bare metal                  |
|--------------------------|---------------------------------|-----------------------------|
| Стек                     | Готовий до `_start`             | Треба налаштувати вручну    |
| `.data` / `.bss`         | Ядро підготовує                 | Startup-код копіює/обнуляє  |
| Тактування               | BIOS/UEFI налаштував            | Startup-код або прошивка    |
| Обробка помилок          | SIGSEGV, core dump              | HardFault → зависання       |
| Діагностика              | strace, /proc, GDB через ptrace | JTAG/SWD, UART, LED         |
| Перший виконуваний рядок | `_start` у `crt0.o`             | Reset handler у startup ASM |

Розуміння цього ланцюжка критичне для дебагу: якщо мікроконтролер не запускається, перевірка йде саме у цьому порядку — чи правильна адреса reset handler у таблиці векторів, чи налаштований стек до першого виклику функції, чи правильно скопійовано `.data` з Flash у RAM, чи збігаються адреси у linker script з реальною картою пам'яті конкретного чіпа. Типова помилка початківця — взяти startup-код від одного мікроконтролера і використати його для іншого з іншим розміром RAM або іншою базовою адресою Flash; результат — тихе пошкодження пам'яті або HardFault відразу після старту. Без знання того, що саме відбувається між увімкненням і першим рядком `main`, будь-яка така проблема є непрозорою.

## 5. Startup code на мікроконтролері (~15 хв)

Startup code — це та частина програми, яку зазвичай не пишуть вручну: вона надходить готовою від виробника чіпа або з HAL-бібліотеки. Проте саме тут відбувається все найважливіше між увімкненням і першим рядком `main`. Розуміння цього коду є обов'язковим для дебагу проблем із запуском і для перенесення проекту на новий мікроконтролер.

### Таблиця векторів переривань

На ARM Cortex-M Flash починається з **таблиці векторів** (Vector Table). Це масив 32-бітних адрес, де кожен елемент — адреса обробника конкретної події:

```
Offset 0x00:  початкове значення SP (не адреса функції — саме значення!)
Offset 0x04:  адреса Reset_Handler
Offset 0x08:  адреса NMI_Handler
Offset 0x0C:  адреса HardFault_Handler
Offset 0x10:  адреса MemManage_Handler
...
Offset 0x40+: адреси обробників периферійних переривань (UART, SPI, TIM...)
```

Процесор при старті читає перші два слова апаратно: перше записує у `MSP` (Main Stack Pointer), по другому стрибає. Якщо адреса обробника у таблиці нечітна (не виставлений біт 0, що є ознакою Thumb-інструкцій) — відразу HardFault.

У C таблицю векторів найзручніше описати як масив вказівників на функції:

```c
/* Тип обробника переривання */
typedef void (*isr_t)(void);

/* Зовнішні символи зі startup ASM або linker script */
extern unsigned long _estack;      /* верх стека — з linker script */
void Reset_Handler(void);
void NMI_Handler(void)       __attribute__((weak, alias("Default_Handler")));
void HardFault_Handler(void) __attribute__((weak, alias("Default_Handler")));

/* Таблиця векторів у спеціальній секції .isr_vector */
__attribute__((section(".isr_vector")))
const isr_t vector_table[] = {
    (isr_t)&_estack,    /* початкове значення SP */
    Reset_Handler,
    NMI_Handler,
    HardFault_Handler,
    /* ... решта виключень і переривань ... */
};

void Default_Handler(void) { while (1); }  /* заглушка для невикористаних */
```

Атрибут `weak alias` дозволяє визначити всі обробники як заглушки за замовчуванням — користувач може перевизначити тільки потрібні, просто написавши функцію з тим самим іменем у своєму файлі.

### Код Reset_Handler: покроковий розбір

Типовий Reset_Handler на ARM Cortex-M у NASM-подібному синтаксисі (GAS ARM Thumb):

```asm
Reset_Handler:
    /* 1. Налаштування тактування (опціонально — може бути у SystemInit) */
    bl      SystemInit          @ викликаємо C-функцію ініціалізації тактування

    /* 2. Копіювання .data з Flash у RAM */
    ldr     r0, =_sdata         @ адреса початку .data у RAM (ціль)
    ldr     r1, =_edata         @ адреса кінця  .data у RAM
    ldr     r2, =_sidata        @ адреса образу .data у Flash (джерело)
copy_data:
    cmp     r0, r1
    bge     zero_bss            @ якщо скопіювали все — переходимо до .bss
    ldr     r3, [r2], #4        @ читаємо слово з Flash, r2 += 4
    str     r3, [r0], #4        @ пишемо у RAM, r0 += 4
    b       copy_data

    /* 3. Обнулення .bss */
zero_bss:
    ldr     r0, =_sbss          @ початок .bss у RAM
    ldr     r1, =_ebss          @ кінець  .bss у RAM
    mov     r2, #0
zero_loop:
    cmp     r0, r1
    bge     call_main
    str     r2, [r0], #4        @ записуємо 0, r0 += 4
    b       zero_loop

    /* 4. Виклик main */
call_main:
    bl      main

    /* 5. Нескінченний цикл якщо main повернула значення */
hang:
    b       hang
```

Символи `_sdata`, `_edata`, `_sidata`, `_sbss`, `_ebss` визначаються у linker script — це межі секцій. Startup-код просто читає їх адреси і виконує цикли копіювання та обнулення.

### Чому .data зберігається у Flash

Глобальна змінна `int counter = 42;` має початкове значення 42. Але RAM при увімкненні містить довільні дані — покластись на те, що там вже 42, неможливо. При цьому Flash (де знаходиться код) — це енергонезалежна пам'ять, і значення 42 там зберігається між вимкненнями. Тому лінкер зберігає **образ** секції `.data` прямо у Flash, поруч із кодом. Startup-код при старті копіює цей образ у RAM на потрібну адресу.

Якщо пропустити цей крок — всі ініціалізовані глобальні змінні матимуть сміттєві значення. Програма може «майже» працювати, якщо значення за збігом виявляться близькими до очікуваних, що робить таку помилку дуже важкою для виявлення. Симптом: після холодного старту (повного знеструмлення) програма поводиться інакше, ніж після теплого (reset без знеструмлення), оскільки RAM зберігає вміст між теплими ресетами.

### Чому .bss треба обнуляти явно

Стандарт C гарантує, що неініціалізовані глобальні і статичні змінні мають значення 0. Під ОС ядро забезпечує це автоматично (нові сторінки пам'яті обнулені). На bare metal — RAM після увімкнення містить довільні дані, і ніхто крім startup-коду це не виправить. Секція `.bss` у Flash взагалі не займає місця (лінкер лише записує її розмір і адресу), тому startup-код мусить обнулити відповідну область RAM самостійно.

### SystemInit і налаштування тактування

Більшість HAL-бібліотек (наприклад, STM32 HAL) виносять ініціалізацію тактування в окрему функцію `SystemInit()`, яку Reset_Handler викликає першою — ще до копіювання `.data`. Це дозволяє писати `SystemInit` на C, хоча вона викликається до повної готовності середовища. Єдина вимога — функція не повинна використовувати глобальних змінних з початковими значеннями (вони ще не скопійовані з Flash) і не покладатись на нульові неініціалізовані змінні (`.bss` ще не обнулено).

### Типові помилки

**Неправильний розмір слова при копіюванні.** Якщо розмір `.data` не кратний 4 байтам, а цикл копіює по 32-бітних словах — останні байти будуть пропущені. Коректний startup-код або вирівнює секції у linker script, або копіює побайтово.

**Виклик функції до встановлення стека.** Якщо `SystemInit` викликається ще до того, як у таблиці векторів правильно вказано початкове значення SP — перший `push` у `SystemInit` запише дані за непередбаченою адресою.

**Забутий виклик `SystemInit`.** При переносі startup-коду між проектами `SystemInit` іноді вилучають «для спрощення». Результат — мікроконтролер працює на внутрішньому RC-генераторі замість PLL, і всі часові характеристики (UART baudrate, таймери) виявляються неправильними.

### Де взяти startup code

На практиці є три джерела:

- **CMSIS + HAL від виробника** (наприклад, STM32CubeMX генерує `startup_stm32xxx.s` автоматично). Це найпоширеніший варіант у промислових проектах.
- **Власний мінімальний startup** — кілька десятків рядків C або ASM, достатніх для конкретного проекту. Добре підходить для навчальних цілей і глибокого розуміння.
- **RTOS-специфічний startup** — FreeRTOS, Zephyr та інші RTOS мають власні startup-файли, що враховують особливості планувальника задач і розподілу стеків між потоками.

У всіх випадках механізм однаковий: таблиця векторів на початку Flash, Reset_Handler, копіювання `.data`, обнулення `.bss`, виклик `main`. Різниця лише у деталях реалізації і обсязі ініціалізованої периферії.

## 6. Linker script для bare metal (~15 хв)

Під час збірки звичайної програми під ОС лінкер використовує вбудований скрипт — він знає стандартний розподіл адресного простору Linux і сам розставляє секції. На bare metal жодних стандартів немає: у кожного мікроконтролера своя адреса Flash, свій обсяг RAM, своя таблиця периферії. Всю цю інформацію треба описати у **linker script** — спеціальному файлі з розширенням `.ld`, який читає GNU ld.

### Структура linker script

Мінімальний linker script для ARM Cortex-M (наприклад, STM32F103 з 64 КБ Flash і 20 КБ RAM):

```ld
/* Точка входу — перший рядок що виконується */
ENTRY(Reset_Handler)

/* Карта пам'яті конкретного чіпа */
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 64K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 20K
}

/* Символ верху стека — кінець RAM */
_estack = ORIGIN(RAM) + LENGTH(RAM);

SECTIONS
{
    /* Таблиця векторів і код — у Flash */
    .isr_vector :
    {
        KEEP(*(.isr_vector))   /* таблиця векторів завжди першою */
    } > FLASH

    .text :
    {
        *(.text*)              /* весь код */
        *(.rodata*)            /* константи і рядки */
        _sidata = .;           /* адреса образу .data у Flash */
    } > FLASH

    /* Дані — у RAM, але образ зберігається у Flash */
    .data :
    {
        _sdata = .;            /* початок .data у RAM */
        *(.data*)
        _edata = .;            /* кінець  .data у RAM */
    } > RAM AT > FLASH         /* VMA = RAM, LMA = Flash */

    /* Неініціалізовані дані — тільки у RAM */
    .bss :
    {
        _sbss = .;
        *(.bss*)
        *(COMMON)
        _ebss = .;
    } > RAM

    /* Стек — у кінці RAM (росте донизу) */
    .stack (NOLOAD) :
    {
        . = ALIGN(8);
        . = . + 0x400;         /* 1 КБ стека */
        . = ALIGN(8);
    } > RAM
}
```

### Ключові концепції

**VMA і LMA.** Кожна секція має дві адреси: **VMA** (Virtual Memory Address) — адреса під час виконання, і **LMA** (Load Memory Address) — адреса де секція зберігається у файлі прошивки. Для `.text` вони збігаються (Flash). Для `.data` — VMA у RAM, LMA у Flash. Саме цю різницю використовує startup-код: він читає по LMA (`_sidata`) і записує по VMA (`_sdata`–`_edata`).

**KEEP.** Директива `KEEP` забороняє лінкеру видалити секцію як «невикористану» при оптимізації. Таблиця векторів не викликається явно з коду — вона просто лежить у Flash. Без `KEEP` лінкер з прапором `--gc-sections` (сміттязбірка секцій) може її видалити, і мікроконтролер не запуститься.

**AT > FLASH.** Синтаксис `> RAM AT > FLASH` вказує: розмісти секцію у RAM (VMA), але зображення у прошивці розташуй одразу після попередньої секції у Flash (LMA). Лінкер автоматично обчислює `_sidata` — адресу початку образу `.data` у Flash.

**Символи меж секцій.** `_sdata`, `_edata`, `_sidata`, `_sbss`, `_ebss` — це не змінні, це **символи лінкера**: числові значення вбудовані у бінарник. Startup-код читає їх за допомогою `ldr r0, =_sdata` — це завантажує саме числове значення адреси, а не вміст за цією адресою. У C-коді ці символи оголошуються як `extern unsigned long _sdata;` і використовуються як `&_sdata` (адреса символу), а не як `_sdata` (що означало б читання з тієї адреси).

**Вирівнювання секцій.** ARM Cortex-M вимагає, щоб доступ до 32-бітних слів відбувався за адресами, кратними 4. Директива `ALIGN(4)` або `ALIGN(8)` у linker script вставляє байти заповнення, щоб наступна секція починалась за вирівняною адресою. Для стека стандарт ARM AAPCS вимагає вирівнювання 8 байт на момент виклику функції. Якщо ігнорувати вирівнювання — можливі як HardFault (на строгих архітектурах), так і тихе сповільнення (процесор робить два звернення до пам'яті замість одного).

### Перевірка результату

Після збірки корисно перевірити розподіл секцій командою:

```bash
arm-none-eabi-size firmware.elf
```
```
   text    data     bss     dec     hex filename
   2048     128     512    2688     A80 firmware.elf
```

`text` — код і константи у Flash; `data` — ініціалізовані глобальні змінні (займають місце і у Flash, і у RAM); `bss` — неініціалізовані (тільки у RAM). Якщо сума `text + data` перевищує розмір Flash — лінкер видасть помилку. Якщо `data + bss` перевищує RAM — теж помилка, але вже під час виконання (стек перезапише `.bss` або навпаки).

Детальнішу карту з адресами кожного символу дає:

```bash
arm-none-eabi-objdump -h firmware.elf   # заголовки секцій
arm-none-eabi-nm --numeric-sort firmware.elf | grep -E "_(s|e)(data|bss|idata|stack)"
```

### Типові помилки

**Відсутній `KEEP` для таблиці векторів.** Мікроконтролер запускається, але при першому перериванні — HardFault, бо таблиця векторів була видалена оптимізатором.

**Переплутані VMA і LMA для `.data`.** Якщо написати `> FLASH` замість `> RAM AT > FLASH`, секція `.data` потрапить у Flash. Читати дані можна, але записати — ні (Flash без спеціальних процедур стирання/запису є read-only). Симптом: будь-яка запис у глобальну змінну мовчки ігнорується або спричиняє HardFault.

**Неправильна `ORIGIN` або `LENGTH`.** Якщо вказати розмір Flash більший за реальний, лінкер не видасть помилки, але частина коду опиниться за межами реальної Flash. На чіпі ці адреси або нічого не містять, або відображені на іншу периферію — поведінка непередбачувана.

### Зв'язок між linker script і startup code

Linker script і startup code — нерозривна пара. Startup-код покладається на символи, які оголошені у linker script (`_sdata`, `_edata`, `_sidata`, `_sbss`, `_ebss`, `_estack`). Linker script покладається на те, що вхідна точка (`Reset_Handler`) і секція `.isr_vector` існують у коді. Якщо змінити імена символів в одному місці і не оновити інше — збірка або провалиться з «undefined symbol», або (гірше) тихо скомпілюється, але запуск буде хибним.

При взятті готового startup-коду з мережі завжди треба перевірити: чи збігаються імена символів у startup з тим, що оголошено у linker script. Різні постачальники використовують різні конвенції: `_sdata` / `__data_start` / `__DATA_BEGIN__` — всі вони означають те саме, але взаємно несумісні між файлами від різних авторів.

### Linker script для x86 bootloader

Для x86 MBR-завантажувача у real mode linker script значно простіший — весь код мусить вміститись у 512 байт і починатись з адреси `0x7C00`:

```ld
ENTRY(_start)

SECTIONS
{
    . = 0x7C00;         /* BIOS завантажує MBR сюди */

    .text : { *(.text*) }
    .data : { *(.data*) }
    .bss  : { *(.bss*)  }

    /* MBR signature: останні два байти мають бути 0x55 0xAA */
    . = 0x7C00 + 510;
    BYTE(0x55)
    BYTE(0xAA)
}
```

Тут немає поняття Flash/RAM — real mode не розрізняє читання і запис пам'яті. Вся секція завантажується BIOS з диска у RAM за адресою `0x7C00` і одразу виконується. Завдання linker script — лише забезпечити правильну базову адресу і MBR-сигнатуру в кінці.

## 7. Переривання: ОС vs bare metal (~15 хв)

Переривання — це механізм, за допомогою якого апаратура повідомляє процесору про подію: прийшов байт через UART, спрацював таймер, натиснута кнопка. Незалежно від того, чи є ОС, апаратний механізм однаковий — процесор зупиняє поточний потік виконання і переходить на обробник. Але все, що відбувається навколо цього переходу — принципово різне під ОС і на bare metal.

### Переривання під ОС

Під ОС застосунок ніколи не взаємодіє з перериваннями напряму. Ядро є єдиним власником таблиці IDT (на x86) або таблиці векторів (на ARM) і реєструє там власні обробники. Коли периферія генерує переривання, ядро обробляє його і доставляє результат до застосунку через абстракції:

- **Файловий дескриптор + `read()`** — ядро блокує процес до готовності даних, прокидає його коли обробник переривання помістив дані у буфер ядра.
- **Сигнали** — ядро надсилає `SIGIO` або `SIGALRM` для асинхронних повідомлень.
- **epoll / kqueue** — ефективне очікування готовності на багатьох дескрипторах одночасно; ядро повідомляє про готовність через переривання від апаратури.

Застосунок повністю ізольований від деталей: не знає, які IRQ-номери використовує UART, не керує пріоритетами переривань, не зберігає регістри — все робить ядро.

### Переривання на bare metal

На bare metal весь цей функціонал ядра відсутній. Програма є єдиним кодом, що виконується, і повністю відповідає за переривання.

**Реєстрація обробника** — це просто запис адреси функції у таблицю векторів (що вже описано у розділі 5). Для ARM Cortex-M:

```c
/* Обробник UART1 у таблиці векторів */
void USART1_IRQHandler(void) {
    if (USART1->SR & USART_SR_RXNE) {       /* є прийнятий байт? */
        char c = USART1->DR;                 /* читаємо — прапор скидається автоматично */
        rx_buffer[rx_head++] = c;
    }
}
```

**Дозвіл переривання** потребує двох кроків: дозволити на рівні периферії (наприклад, `USART1->CR1 |= USART_CR1_RXNEIE`) і дозволити у контролері переривань **NVIC**:

```c
NVIC_EnableIRQ(USART1_IRQn);               /* дозволяємо у NVIC */
NVIC_SetPriority(USART1_IRQn, 1);          /* пріоритет 1 (0 — найвищий) */
__enable_irq();                             /* глобальне дозволення (знімає маску PRIMASK) */
```

### Що робить процесор автоматично при вході в обробник

ARM Cortex-M автоматично зберігає на стеку вісім регістрів перед входом в обробник: `r0`, `r1`, `r2`, `r3`, `r12`, `lr`, `pc`, `xpsr`. Це означає, що обробник, написаний на C, може використовувати ці регістри вільно — вони вже збережені апаратно. Регістри `r4`–`r11` апаратура не зберігає — їх зберігає компілятор за правилами ABI, якщо функція їх використовує.

На **x86** у real mode і protected mode все навпаки: апаратура зберігає тільки `cs`, `ip`, `flags` (і `ss`, `sp` при зміні привілеїв). Всі інші регістри — відповідальність обробника. Типовий пролог x86-обробника:

```nasm
irq_handler:
    pusha               ; зберігаємо всі регістри загального призначення
    push ds
    push es
    ; ... обробка ...
    pop  es
    pop  ds
    popa
    iret                ; повернення: відновлює ip, cs, flags
```

### Пріоритети і вкладені переривання

ARM Cortex-M підтримує **вкладені переривання**: обробник з вищим пріоритетом може перервати обробник з нижчим. NVIC (Nested Vectored Interrupt Controller) керує цим апаратно — не потрібно писати жодного коду для підтримки вкладеності. Важливо лише правильно розставити пріоритети: критичні обробники (наприклад, ШІМ-генератор або захист від перенапруги) — з низьким числовим значенням пріоритету (0 або 1), менш критичні (UART, SPI для логування) — з вищим числовим значенням.

Якщо два переривання з однаковим пріоритетом надійдуть одночасно — NVIC обирає те, що має менший номер у таблиці векторів. Це детерміновано і передбачувано — важлива властивість для систем реального часу.

### Обробник: правила написання

Обробник переривань на bare metal повинен дотримуватись суворих правил:

- **Мінімум роботи.** Обробник має виконуватись якомога швидше. Ідеальна схема: прийняти байт → покласти у кільцевий буфер → вийти. Всю подальшу обробку — в основному циклі.
- **Без блокуючих викликів.** Жодного `while (!(USART->SR & TXE));` в обробнику — це заблокує весь процесор і не дасть іншим перериванням виконатись.
- **Volatile для спільних змінних.** Будь-яка змінна, яку обробник переривань і основний код читають або записують спільно, мусить бути оголошена `volatile`. Інакше компілятор може закешувати її у регістрі й не помітити змін, зроблених обробником.
- **Атомарність критичних секцій.** Якщо основний код читає багатобайтову структуру, яку обробник може змінити посередині — на час читання треба вимкнути переривання (`__disable_irq()`) і одразу ввімкнути назад.

### Латентність і детермінізм

Одна з головних переваг bare metal над ОС — **детермінована латентність** реакції на переривання. На ARM Cortex-M без ОС від моменту апаратної події до першої інструкції обробника — фіксовані 12 тактів (плюс час завершення поточної інструкції, максимум кілька тактів). Це критично для систем реального часу: мотор-контролер, що управляє ШІМ, або протокол з жорсткими часовими обмеженнями (CAN, LIN) не може допустити нефіксованої затримки.

Під ОС загального призначення той самий сигнал проходить через планувальник, можливе переключення контексту, і реакція може затриматись на мілісекунди. RTOS (FreeRTOS, Zephyr) знаходяться посередині: вони дають передбачуванішу латентність ніж ОС загального призначення, але дещо більшу ніж голий bare metal.

### Типові помилки

**Відсутній `volatile`.** Найпоширеніша помилка:

```c
uint8_t flag = 0;

void TIM2_IRQHandler(void) { flag = 1; }  /* переривання встановлює прапор */

int main(void) {
    while (!flag) { /* чекаємо */ }       /* компілятор може закешувати flag у регістрі */
}
```

Без `volatile uint8_t flag` компілятор побачить, що `flag` не змінюється всередині `while`, і перетворить цикл на `while (1)`. Програма зависне назавжди, хоча обробник переривання сумлінно виконує `flag = 1`.

**Незакритий прапор переривання.** Якщо обробник не скинув прапор готовності у регістрі периферії — після повернення з обробника процесор одразу знову увійде в нього, оскільки апаратний сигнал залишається активним. Результат: нескінченний вхід в обробник, основний цикл ніколи не отримує керування.

**Надто довгий обробник.** Якщо обробник UART-переривання виконує розбір протоколу, форматування рядків або запис у Flash — інші переривання чекатимуть. За цей час можна пропустити наступний байт (переповнення буфера периферії) або прострочити реакцію на більш пріоритетну подію.

### Порівняння підходів

| Аспект                   | Під ОС                        | Bare metal                      |
|--------------------------|-------------------------------|---------------------------------|
| Реєстрація обробника     | `sigaction`, `epoll_ctl`      | Запис адреси у таблицю векторів |
| Збереження регістрів     | Ядро                          | Апаратура (частково) + компілятор |
| Пріоритети               | Планувальник ядра             | NVIC / програмний контроль      |
| Доставка до застосунку   | Сигнал або fd-подія           | Пряме виконання обробника       |
| Помилка в обробнику      | SIGSEGV, core dump            | HardFault → зависання           |

## 8. Як виглядає мінімальна програма без ОС (~15 хв)

Найкращий спосіб закріпити матеріал усієї лекції — побачити повну мінімальну програму цілком: від першого слова у Flash до блимання світлодіода. У цьому розділі наведено два приклади: ARM Cortex-M (мікроконтролер) і x86 real mode (bootloader). Обидва запускаються без жодної ОС і жодної сторонньої бібліотеки.

### Приклад 1: ARM Cortex-M — блимання світлодіодом

Повна програма для STM32F103 (Blue Pill) складається з трьох файлів.

**`startup.c`** — таблиця векторів і Reset_Handler:

```c
extern unsigned long _estack;
extern void main(void);

void Default_Handler(void) { while (1); }
void Reset_Handler(void);

__attribute__((section(".isr_vector")))
void (*const vectors[])(void) = {
    (void*)&_estack,
    Reset_Handler,
    Default_Handler,  /* NMI */
    Default_Handler,  /* HardFault */
};

extern unsigned long _sdata, _edata, _sidata, _sbss, _ebss;

void Reset_Handler(void) {
    /* копіювання .data з Flash у RAM */
    unsigned long *src = &_sidata, *dst = &_sdata;
    while (dst < &_edata) *dst++ = *src++;
    /* обнулення .bss */
    dst = &_sbss;
    while (dst < &_ebss) *dst++ = 0;
    main();
    while (1);
}
```

**`main.c`** — керування GPIO напряму через регістри периферії:

```c
/* Регістри RCC і GPIOC для STM32F103 */
#define RCC_APB2ENR  (*(volatile unsigned*)0x40021018)
#define GPIOC_CRH    (*(volatile unsigned*)0x40011004)
#define GPIOC_ODR    (*(volatile unsigned*)0x4001100C)

void delay(volatile unsigned n) { while (n--); }

void main(void) {
    RCC_APB2ENR |= (1 << 4);          /* тактування GPIOC */
    GPIOC_CRH   &= ~(0xF << 20);      /* PC13: очищаємо конфігурацію */
    GPIOC_CRH   |=  (0x2 << 20);      /* PC13: вихід, push-pull, 2 МГц */

    while (1) {
        GPIOC_ODR ^= (1 << 13);        /* інвертуємо PC13 */
        delay(500000);
    }
}
```

Тут немає `#include`, немає `HAL_GPIO_TogglePin` — лише прямий запис у регістри за адресами з datasheet. Адреса `0x40021018` — це точна адреса регістра `RCC_APB2ENR` у адресному просторі STM32. Саме так і працює вся периферія на bare metal: кожен регістр має фіксовану адресу, і взаємодія з залізом — це звичайний запис і читання пам'яті.

Важлива деталь у `main.c` — декларація `volatile unsigned` для регістрів периферії. Без `volatile` компілятор може вирішити, що повторний запис в одну адресу є зайвим і оптимізувати його геть, або перекомпонувати порядок операцій. Апаратура цього не пробачає: регістр `CRH` мусить бути налаштований до того, як починається переключення `ODR`, і ніякий компілятор не повинен змінювати цей порядок.

**Збірка:**

```bash
arm-none-eabi-gcc -mcpu=cortex-m3 -mthumb -nostdlib -T stm32.ld \
    startup.c main.c -o firmware.elf
arm-none-eabi-objcopy -O binary firmware.elf firmware.bin
# прошивка: st-flash write firmware.bin 0x08000000
```

Прапор `-nostdlib` вказує компілятору не додавати `crt0.o` і не підключати `libc` — весь startup надає наш `startup.c`.

### Приклад 2: x86 MBR bootloader — виведення рядка

Мінімальний x86 bootloader у 512 байтах real mode, що виводить рядок через BIOS:

```nasm
; bootloader.asm — NASM, real mode, завантажується BIOS за адресою 0x7C00
[BITS 16]
[ORG 0x7C00]

start:
    ; налаштування сегментних регістрів
    xor  ax, ax
    mov  ds, ax
    mov  es, ax

    ; виведення рядка через BIOS int 0x10 (teletype output)
    mov  si, msg
.loop:
    lodsb                    ; завантажуємо наступний байт рядка у al
    test al, al              ; нульовий байт = кінець рядка
    jz   .halt
    mov  ah, 0x0E            ; функція 0x0E: виведення символу
    mov  bh, 0               ; сторінка відео
    int  0x10                ; виклик BIOS
    jmp  .loop

.halt:
    cli                      ; вимикаємо переривання
    hlt                      ; зупиняємо процесор

msg db "Hello from bare metal!", 13, 10, 0

; заповнення до 510 байт і MBR-сигнатура
times 510 - ($ - $$) db 0
dw 0xAA55
```

**Збірка і запуск:**

```bash
nasm -f bin bootloader.asm -o bootloader.bin
# запуск у QEMU без жодної ОС:
qemu-system-x86_64 -drive format=raw,file=bootloader.bin
```

QEMU завантажує `bootloader.bin` як диск, бачить сигнатуру `0xAA55` в кінці, вважає сектор завантажувальним і передає на нього керування. Весь вивід — через BIOS interrupt, без жодного драйвера, без ОС.

Зверніть увагу на `[ORG 0x7C00]` — директива NASM, яка повідомляє асемблеру базову адресу коду. Без неї адреси мітки `msg` будуть відраховуватись від нуля, а не від `0x7C00`, і `lodsb` читатиме не рядок, а довільну пам'ять. Це аналог того, що робить linker script для ARM: вказує де у пам'яті знаходиться код, щоб усі адреси у бінарнику були коректними.

### Що спільного між двома прикладами

Обидва приклади демонструють один і той самий принцип, що різним чином реалізований на двох архітектурах:

- **Перша інструкція** визначається апаратурою (reset vector / BIOS → `0x7C00`).
- **Стек** або підготовлений до першої інструкції (ARM: апаратно зі слова у Flash) або налаштовується явно (x86: `mov sp, 0x7C00` у завантажувачі при потребі).
- **Периферія** — пряма взаємодія з регістрами за відомими адресами (STM32 GPIO) або через BIOS-сервіси (x86 int 0x10).
- **Нескінченний цикл** або `hlt` в кінці — програма не може «завершитись», бо немає ОС, яка б прийняла управління назад.

Ці два приклади разом охоплюють весь матеріал лекції: ELF і запуск під ОС — це один полюс; MBR і ARM startup — інший. Між ними лежить весь спектр системного програмування, але механізми скрізь одні й ті самі.

### Наступні кроки: від мінімального до реального

Мінімальна програма — відправна точка. Реальні bare metal проекти нарощують складність поступово:

- **UART-діагностика** — першою додають функцію `print_uart`, яка пише байти напряму у регістр UART. Це замінює відладчик там де JTAG недоступний: програма сама розповідає що відбувається.
- **Таймерні переривання** — SysTick на ARM Cortex-M генерує переривання кожну мілісекунду. На основі лічильника переривань реалізується `delay_ms` без холостих циклів і базові часові виміри.
- **Кільцеві буфери для UART** — обробник переривання від UART пише у кільцевий буфер, основний цикл читає з нього. Це стандартний патерн для асинхронного вводу-виводу на bare metal.
- **Bootloader другого рівня** — програма у Flash може перевіряти наявність нової прошивки (наприклад, отриманої через UART) і самостійно перезаписувати себе. Саме так влаштовані DFU-завантажувачі і OTA-оновлення.

Кожен із цих кроків спирається на знання з цієї лекції: startup code, linker script, переривання, системний стек адресації периферії. Розуміння того, що відбувається між увімкненням і першим рядком `main`, перетворює bare metal з «чорної магії» на передбачувану і налагоджувану інженерну дисципліну.
