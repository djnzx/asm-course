# Лекція 13: Взаємодія Assembler, C та інших мов програмування

## 1. Навіщо це взагалі потрібно (~10 хв)

Ніхто не пише великі програми повністю на асемблері. Але асемблер нікуди не зник — він живе поруч із C, C++, Rust та іншими мовами в одному бінарнику. Ось типові причини чому:

### Продуктивність у вузьких місцях

Компілятори дуже хороші в оптимізації загального коду, але вони не всесильні. У критичних секціях — обробка відео, шифрування, чисельні методи, стиснення даних — рукописний ASM може бути у 2–5 разів швидшим за те, що генерує навіть найагресивніший компілятор. Причина проста: компілятор мусить бути консервативним і коректним для всіх можливих вхідних даних, тоді як програміст знає конкретний контекст і може вручну розкласти цикл, вибрати потрібні SIMD-інструкції (`AVX2`, `SSE4`), або уникнути зайвих завантажень з пам'яті. Саме тому ядра криптографічних бібліотек (OpenSSL, libsodium) та мультимедійних кодеків (x264, FFmpeg) містять ретельно написані ASM-функції, які викликаються з C через звичайний механізм лінкування.

### Апаратний доступ

Деякі речі просто неможливо зробити з C без ASM. Інструкції `cpuid` (визначення можливостей процесора), `rdtsc` (читання лічильника тактів), `in`/`out` (порти вводу-виводу в режимі ядра), `lgdt`/`lidt` (завантаження таблиць дескрипторів), `hlt`, `cli`/`sti` — всі вони недоступні як C-вирази. Операційні системи, гіпервізори, BIOS/UEFI-прошивки, завантажувачі та драйвери низького рівня вимушені використовувати ASM для ініціалізації: перемикання між режимами процесора, налаштування стека, встановлення сторінкових таблиць. Навіть у Linux kernel є файли `.S` та `inline asm` саме з цієї причини — не заради швидкості, а тому що іншого способу немає.

### C як lingua franca міжмовної взаємодії

Більшість фундаментальних бібліотек написані на C: `libc`, OpenSSL, SQLite, zlib, libpng, libcurl. Кожна мова програмування — Python, Ruby, Go, Rust, Java через JNI — рано чи пізно мусить звертатись до цього коду. C виграв роль посередника не через красу мови, а через простоту свого ABI: немає name mangling, немає рантайм-залежностей, стабільний calling convention. Тому "вміти викликати C" — це по суті "вміти взаємодіяти з більшістю існуючого системного ПЗ". Саме ця роль робить знання C ABI та calling conventions обов'язковим для будь-якого системного програміста.

### Легасі та вбудовані системи

У промисловості та вбудованих системах існує колосальна кількість написаного на ASM коду з 1980–90-х років — драйвери для промислових контролерів, прошивки телекомунікаційного обладнання, алгоритми реального часу для DSP. Цей код нікуди не зникає: переписувати його дорого, ризиковано і часто просто заборонено (сертифікований медичний чи авіаційний софт). Натомість його інтегрують у нові системи через лінкування з C або C++, і тоді важливо розуміти, як забезпечити коректну передачу параметрів, вирівнювання стека та збереження регістрів. Знання взаємодії ASM і C — це практична необхідність для будь-кого, хто працює з embedded, RTOS або legacy-кодовою базою.

### Розуміння того, що робить компілятор

Навіть якщо виніколи не будете писати ASM у продакшені, вміння його читати — безцінне. Коли профайлер показує, що функція повільна, ви дивитесь у дизасемблер і бачите: компілятор не векторизував цикл, або зробив зайвий `call` замість inline, або не зміг елімінувати перевірку на `null`. Розуміння генерованого коду дозволяє осмислено використовувати `__attribute__`, `volatile`, `restrict`, прагми оптимізації. Крім того, дебаг на межі мов — C + ASM або C + Rust FFI — майже завжди вимагає зануритись у регістри та стек у GDB, і без базового розуміння ASM ви будете безпорадні.

---

Ключова ідея: **всі мови в кінці стають об'єктними файлами**. Якщо вони дотримуються одних і тих самих правил (ABI, calling convention, формат символів) — вони можуть взаємодіяти.

## 2. Лінкування — деталі процесу (~10 хв)

Перш ніж говорити про виклики між мовами, треба зрозуміти що відбувається після того, як компілятор завершив роботу. Компілятор виробляє **об'єктний файл** — це ще не виконуваний бінарник, а лише підготовлений "шматок" коду і даних, у якому частина адрес ще невідома. Завдання **лінкера** — зібрати кілька таких шматків разом і отримати фінальний виконуваний файл або бібліотеку.

### Що таке об'єктний файл: секції

Об'єктний файл організований у **секції** (sections) — іменовані блоки з різним призначенням:

- `.text` — скомпільований машинний код функцій. Тільки для читання і виконання.
- `.data` — ініціалізовані глобальні та статичні змінні (наприклад, `int x = 42;`). Читання і запис.
- `.bss` — неініціалізовані глобальні змінні (`int y;`). У файлі займають нуль байт — лише записується розмір, ОС заповнить нулями при завантаженні.
- `.rodata` — константи тільки для читання: рядкові літерали, `const`-змінні.
- `.rel.text` / `.rela.text` — таблиця релокацій для секції `.text` (про це далі).

Розуміння секцій пояснює, чому `int x = 0;` та `int x;` поводяться по-різному в пам'яті і чому статичні бібліотеки можуть "роздмухуватись" при включенні зайвих об'єктних файлів.

### Таблиця символів: defined vs undefined

Кожен об'єктний файл містить **таблицю символів** — список імен (функцій, змінних) разом з їхніми атрибутами. Символи бувають двох типів:

- **Defined (визначені)** — символ реалізований у цьому файлі. Наприклад, функція `add` у `math.o` визначена і має конкретну адресу відносно початку секції `.text`.
- **Undefined (невизначені)** — символ використовується, але реалізований деінде. Наприклад, якщо `main.o` викликає `printf`, то `printf` буде невизначеним символом у `main.o` — лінкер знайде його у `libc`.

Лінкер перебирає всі об'єктні файли і зіставляє undefined-символи з defined. Якщо якийсь символ залишається невизначеним після перегляду всіх файлів і бібліотек — ви отримуєте добре знайому помилку `undefined reference to 'foo'`.

### Relocations: залатати адреси

Коли компілятор генерує виклик функції `call foo`, він не знає, де `foo` опиниться у фінальному бінарнику. Тому він ставить у машинний код заглушку (нулі або відносний offset 0) і записує у таблицю релокацій: "тут, зі зміщенням X у секції `.text`, стоїть посилання на символ `foo` — коли знатимеш адресу, підстав її".

Лінкер, розміщуючи всі секції у пам'яті, знає фінальні адреси всіх символів і проходить по таблиці релокацій, **патчуючи** машинний код. Це і є процес релокації. Для динамічних бібліотек частина релокацій відкладається на момент завантаження — їх виконує **dynamic linker** (`ld.so`), що дозволяє бібліотекам завантажуватись за будь-якою адресою (Position Independent Code, PIC).

### Статичне vs динамічне лінкування

**Статичне лінкування** (`gcc -static`): лінкер копіює увесь необхідний код з бібліотек прямо у виконуваний файл. Результат — один самодостатній бінарник без зовнішніх залежностей. Мінус: великий розмір; якщо `libc` оновиться (наприклад, патч безпеки), ваш бінарник не отримає виправлення без перекомпіляції.

**Динамічне лінкування** (за замовчуванням): у бінарнику зберігаються лише **імена** потрібних бібліотек і символів. При запуску `ld.so` знаходить бібліотеки на диску, відображає їх у пам'ять і виконує залишкові релокації. Кілька процесів можуть ділити один екземпляр `.so` у пам'яті. Саме тому `ldd ./my_program` показує список залежностей — це перелік `.so`-файлів, які `ld.so` знайде при запуску.

### Linker script: хто вирішує де що лежить

Лінкер не довільно розкидає секції у пам'яті — він слідує **linker script** (`.ld`-файлу). Скрипт описує карту пам'яті: куди покласти `.text`, звідки починається `.data`, де межа між RAM і ROM (критично для мікроконтролерів). У звичайних Linux-програмах використовується вбудований скрипт `ld` за замовчуванням, але у embedded та OS-розробці кастомні linker scripts — норма. Вони дозволяють, наприклад, розмістити вектори переривань за адресою `0x00000000` або вказати, що певна функція має лежати у швидкій SRAM, а не у Flash.

## 3. Формат об'єктних файлів (~18 хв)

Компілятор зробив свою роботу і зберіг результат у файл. Але що це взагалі за файл? Це не просто машинний код від першого до останнього байта — це структурований контейнер зі своєю внутрішньою організацією. І ця організація має назву — **формат об'єктного файлу**.

Різні операційні системи використовують різні формати. Linux — ELF, Windows — PE, macOS — Mach-O. Але всі вони вирішують одне й те саме завдання: пояснити лінкеру та операційній системі, що саме лежить у цьому файлі і що з ним робити. Без цієї структури лінкер не знав би де код, а де дані, де список залежностей, а де таблиця релокацій.

### Аналогія: посилка з супровідним листом

Уявіть, що об'єктний файл — це посилка на складі. Зовні — наклейка з метаданими: звідки, для якої платформи, якого типу вміст. Всередині — вміст розкладений по відсіках із підписами: "тут машинний код", "тут ініціалізовані дані", "тут список символів", "тут інструкції для лінкера — де підставити адреси". Ці відсіки і є секціями, про які ми говорили раніше.

Лінкер — це сортувальник на складі. Він відкриває кілька посилок, виймає відсіки з однаковими підписами, складає їх разом і запаковує у фінальну посилку — виконуваний файл. Операційна система потім відкриває цю фінальну посилку і завантажує вміст у пам'ять, знову орієнтуючись на ті самі підписи.

### ELF — формат для Linux і Unix-світу

ELF з'явився у 1990-х як єдиний стандарт для Unix-подібних систем, і з тих пір він живе скрізь: Linux, Android, FreeBSD, Solaris. Одна з головних його переваг — універсальність. Один і той самий формат описує і об'єктний файл після компіляції, і виконуваний файл після лінкування, і динамічну бібліотеку. Тип файлу записаний у заголовку, і лінкер або ОС зчитують його першим ділом.

Важлива концептуальна деталь ELF: у ньому є два різних погляди на один і той самий файл. **Погляд лінкера** — це секції: маленькі іменовані блоки з різним призначенням, кожен зі своїми атрибутами. **Погляд операційної системи** — це сегменти: великі блоки пам'яті з правами доступу, у які упаковані секції. Коли ви пишете код і компілюєте його — ви у світі секцій. Коли програма запускається і ОС відображає файл у пам'ять — вона дивиться на сегменти. В один сегмент "тільки для читання і виконання" потрапляє і код, і рядкові константи; в окремий сегмент "читання і запис" — змінні і дані. Це не просто організаційне рішення — це безпека: якщо код і дані лежать у різних сегментах з різними правами, то випадкова (або навмисна) запис у код стає неможливою на рівні процесора.

### PE — формат Windows із корінням у DOS

PE — Portable Executable — формат усіх виконуваних файлів і бібліотек Windows: `.exe`, `.dll`, `.sys`. Він старший за ELF і несе на собі відбиток своєї епохи. Перше, що можна побачити у будь-якому `.exe` — це маленька DOS-програма, яка виводить "This program cannot be run in DOS mode" і завершується. Це не баг і не жарт — це реліктовий шар сумісності з часів, коли DOS і Windows існували паралельно і один і той самий файл міг потрапити в обидві системи. Сьогодні ця програма — просто ритуальний артефакт у кожному Windows-бінарнику.

За цим рудиментом іде власне PE-структура. Принципова відмінність від ELF у тому, як описуються зовнішні залежності. У PE є явний **список експортів** — що ця бібліотека пропонує іншим, і явний **список імпортів** — що вона сама потребує від зовнішніх DLL. Саме цей список імпортів Windows читає при запуску програми і вирішує, які DLL треба знайти і підвантажити. Якщо потрібна DLL не знайдена — програма не запуститься з помилкою про відсутність бібліотеки. Це точний аналог того, що `ldd` показує на Linux.

Ще одна особливість PE: він явно відокремлює адресу, за якою хотів би завантажитись (preferred base address), від реальної. Якщо ця адреса зайнята, Windows перемістить бібліотеку і виправить усі внутрішні посилання — це і є runtime-релокація, яка на Linux виконується по-іншому, через позиційно-незалежний код.

### Mach-O — формат Apple і ідея "один файл для всіх"

Mach-O — формат macOS і iOS. Структурно він схожий на ELF: заголовок, потім список описувачів що і де лежить, потім самі дані. Але є одна особливість, якої немає ані в ELF, ані в PE: підтримка кількох архітектур в одному файлі.

Коли Apple переходила з PowerPC на Intel у 2006-му, а потім з Intel на власні чіпи M1 у 2020-му — перед розробниками стояла проблема: як поширювати одну програму, яка працює на обох архітектурах? Рішення Apple — "товстий бінарник" (fat binary або Universal Binary): один `.app`-файл всередині містить два повноцінних варіанти коду — для Intel і для ARM. Операційна система при запуску дивиться на поточну архітектуру і вибирає потрібний шматок. Для користувача це абсолютно прозоро.

Крім цього, Mach-O використовує концепцію "команд завантаження" — список інструкцій для системного завантажувача: які сегменти відобразити у пам'ять, де знайти динамічний лінкер, звідки починати виконання, які зовнішні бібліотеки потрібні. Це гнучкіша модель, ніж фіксована структура PE, але концептуально вирішує ту саму задачу.

### Три інструменти, які потрібно знати

Знати формати в теорії добре. Вміти їх читати на практиці — набагато корисніше. На Linux для роботи з ELF є три утиліти, які постійно використовуються у реальній роботі.

**`nm`** — найпростіший спосіб подивитись таблицю символів. Він виводить список: ім'я символу, його тип і де він знаходиться. Тип позначається буквою: `T` — функція у коді, `D` — змінна у даних, `U` — символ невизначений, очікує лінкера. Коли ви отримуєте помилку "undefined reference" — перший крок: запустити `nm` на підозрілому об'єктнику і перевірити, чи справді там є потрібний символ.

**`readelf`** — повноцінний інспектор ELF-файлу. Він покаже заголовок, список секцій із їхніми розмірами і атрибутами, таблицю символів у детальному вигляді, таблицю релокацій — тобто список місць у коді, де лінкер мусить підставити адреси. Якщо `nm` — це погляд з висоти, то `readelf` — це погляд під мікроскопом.

**`objdump`** — швецький ніж серед цих утиліт. Крім усього, що вміє `readelf`, він дизасемблює машинний код назад у читабельні інструкції. Це незамінно коли треба перевірити що саме згенерував компілятор, чи правильно виконалась оптимізація, або де саме програма робить щось несподіване.

### Як це виглядає на практиці

Типовий сценарій: ви написали функцію на асемблері, скомпілювали C-файл, і при лінкуванні отримали помилку. Перший крок — `nm` на обидва об'єктних файли. В одному функція помічена як `U` — undefined. В іншому вона має бути `T` — defined. Якщо її там немає або ім'я відрізняється на один символ — ви знайшли проблему. Без розуміння цієї механіки ви б просто дивились на повідомлення про помилку і не знали з якого боку підходити.

Саме тому формат об'єктних файлів — це не академічна деталь. Це словник, без якого ви не зможете прочитати те, що лінкер намагається вам сказати.

## 4. Calling conventions (~17 хв)

Ми вже знаємо, що лінкер зшиває об'єктні файли разом і вирішує проблему адрес. Але є інша проблема, яку лінкер не вирішує: коли одна функція викликає іншу — як саме вона передає аргументи? Де чекати результат? Хто прибирає за собою на стеку? Це питання не до лінкера — це питання до **угоди про виклик**, або calling convention.

### Чому потрібна угода

Уявіть двох людей, які домовились разом зробити справу, але не узгодили деталей. Один приніс матеріали і поклав їх ліворуч від дверей. Другий прийшов і пошукав їх праворуч — нічого немає. Обидва зробили все "правильно" зі свого погляду, але взаємодія провалилась.

Те саме відбувається з функціями. Якщо викликаючий код (caller) кладе перший аргумент у регістр `rdi`, а функція (callee) очікує його знайти у регістрі `rcx` — нічого не спрацює. Якщо caller не вирівняв стек, а функція покладається на вирівнювання — в кращому випадку буде падіння, у гіршому — тихий баг у розрахунках.

Calling convention — це саме та угода. Вона відповідає на чотири запитання: де передаються аргументи, де повертається результат, хто зберігає регістри і хто прибирає стек після виклику.

### System V AMD64 ABI — угода Linux і macOS

На Linux (і на macOS теж) діє **System V AMD64 ABI**. Це відкритий стандарт, прийнятий ще на початку 2000-х, і сьогодні його дотримуються GCC, Clang і будь-який інший компілятор для цих платформ.

**Передача аргументів.** Перші шість цілочисельних аргументів і вказівників передаються через регістри: `rdi`, `rsi`, `rdx`, `rcx`, `r8`, `r9` — саме у такому порядку. Тобто якщо ви викликаєте функцію з трьома аргументами, перший йде у `rdi`, другий у `rsi`, третій у `rdx`. Сьомий і наступні аргументи кладуться на стек — справа наліво, тобто останній аргумент виштовхується першим.

Для аргументів з плаваючою комою діє окрема черга: `xmm0` через `xmm7`. Вони не перетинаються з цілочисельними регістрами, тому функція може одночасно отримати три int-и через `rdi`/`rsi`/`rdx` і два double через `xmm0`/`xmm1`.

**Повернення результату.** Цілочисельний або вказівниковий результат повертається у регістрі `rax`. Якщо результат — 128-бітне значення, використовуються `rax` і `rdx` разом. Результат з плаваючою комою повертається у `xmm0`.

**Збереження регістрів.** Тут є важливий поділ на дві групи. **Caller-saved регістри** — це ті, що функція може вільно змінювати, не зберігаючи: `rax`, `rcx`, `rdx`, `rsi`, `rdi`, `r8`–`r11`, всі `xmm`-регістри. Якщо caller хоче зберегти значення у `rdi` після виклику — він сам повинен його врятувати перед `call`. **Callee-saved регістри** — це ті, що функція зобов'язана відновити перед поверненням: `rbx`, `rbp`, `r12`–`r15`. Якщо функція хоче використати `rbx` — вона мусить спочатку зберегти його на стеку і відновити у кінці.

Чому саме такий поділ? Це компроміс між зручністю для коротких функцій (не треба зберігати багато регістрів, якщо функція їх не використовує) і надійністю для довгих функцій (можна спокійно тримати змінні у callee-saved регістрах упродовж усього тіла функції).

### Вирівнювання стека: правило 16 байт

Є ще одне правило ABI, яке новачки часто ігнорують і потім довго шукають причину падіння: **перед інструкцією `call` стек мусить бути вирівняний на 16 байт**.

Чому? Сучасні SIMD-інструкції (SSE, AVX) працюють із 128- і 256-бітними регістрами і вимагають, щоб дані у пам'яті лежали за адресою, кратною 16 або 32. Якщо функція хоче зберегти або завантажити `xmm`-регістр зі стека — вона розраховує на вирівнювання. Порушення цієї вимоги призводить до виключення процесора при виконанні відповідної інструкції.

Але тут є тонкість: сама інструкція `call` кладе на стек адресу повернення — 8 байт. Якщо перед `call` стек вирівняний на 16, то одразу на початку функції він стає зміщеним на 8. Тому у пролозі функції зазвичай є `push rbp` — це ще 8 байт, і вирівнювання відновлюється. Це не випадковість, це частина угоди.

На практиці якщо ви пишете ASM-функцію, яка сама викликає інші функції, ви мусите явно стежити за вирівнюванням. Стандартна помилка — забути, що непарна кількість `push`-ів зламає вирівнювання, і `call printf` впаде у самому несподіваному місці.

### Red zone — подарунок для листкових функцій

На Linux є ще одна зручність, яка відсутня на Windows: **red zone**. Це 128 байт нижче поточного значення `rsp`, які функція може вільно використовувати як тимчасовий простір — без жодного `sub rsp, N` і без ризику, що ці байти хтось перепише.

Чому це безпечно? Тому що у звичайному контексті нікого нема, хто б писав нижче `rsp` — сигнали та переривання ядра зберігають стан вище поточного стека, не нижче. Тому листкова функція (та, що не викликає інших функцій) може тримати свої локальні змінні у red zone і заощадити два рядки коду на маніпуляціях зі стеком.

Але є умова: щойно функція робить `call` — red zone знищується, бо `call` декрементує `rsp`. Тому red zone — виключно для листкових функцій.

### x64 Windows ABI — схоже, але інше

Windows використовує власну угоду, і вона відрізняється від System V у кількох ключових місцях. Якщо ви пишете код, що має працювати на обох платформах, або викликаєте Windows API з ASM — ці відмінності треба знати напам'ять, бо помилки тут не завжди очевидні.

**Аргументи.** На Windows перші чотири аргументи передаються через `rcx`, `rdx`, `r8`, `r9` — а не через `rdi`/`rsi`/`rdx`/`rcx` як на Linux. Тобто перший аргумент іде у `rcx`, а не у `rdi`. Це означає, що той самий ASM-код, що правильно приймає аргументи на Linux, прийме неправильні значення на Windows.

**Shadow space.** На Windows caller зобов'язаний зарезервувати на стеку 32 байти перед `call` — так зване "тіньове місце" (shadow space або home space). Це 4 слоти по 8 байт — місця для збереження чотирьох регістрових аргументів, якщо функція захоче їх спиллити на стек. Функція може або не може використовувати це місце, але воно має бути виділене у будь-якому випадку. На Linux нічого схожого немає.

**Callee-saved регістри.** Список ширший: `rbx`, `rbp`, `rdi`, `rsi`, `r12`–`r15` і навіть частина `xmm`-регістрів (`xmm6`–`xmm15`). Зверніть увагу: `rdi` і `rsi` на Windows є callee-saved, а на Linux — caller-saved і використовуються для передачі аргументів. Це одна з найпоширеніших пасток при портуванні ASM між платформами.

**Немає red zone.** На Windows red zone відсутня. Будь-яке використання пам'яті нижче `rsp` без явного декременту — некоректно.

### Чому це важливо саме зараз

Calling convention — це клей між мовами. Якщо C-код викликає ASM-функцію, вона мусить дотримуватись тієї самої угоди, що і будь-яка C-функція на цій платформі. Якщо ASM-код викликає `printf` — він мусить передати аргументи точно так, як очікує `printf`. Порушення угоди не обов'язково одразу призводить до падіння — іноді код "майже працює", але час від часу повертає сміттєві значення або псує чужі дані.

Розуміння calling convention — це розуміння мови, якою розмовляють функції між собою. Без цього написати коректний міжмовний виклик неможливо.

## 5. Name mangling (~15 хв)

Ми вже знаємо, що лінкер зшиває символи між файлами за іменами. Один файл визначає символ `add`, інший оголошує його як зовнішній — лінкер знаходить збіг і з'єднує. Але що саме є "ім'ям" символу? Виявляється, це залежить від мови — і тут починається одна з найпідступніших пасток у міжмовній взаємодії.

### Чому в C++ одного імені недостатньо

У мові C кожна функція має унікальне ім'я. Двох функцій `add` в одній програмі бути не може — якщо є дві, це помилка компіляції. Тому символ у таблиці символів отримує рівно те ім'я, яке написав програміст: `add`, і більше нічого.

C++ зламав цю просту картину, ввівши **перевантаження функцій**: можна написати `add(int, int)` і `add(double, double)` — і це дві різні функції з однаковим ім'ям. Але лінкер не знає C++ — він оперує символами, і символи мусять бути унікальними рядками. Тому компілятор C++ не може покласти у таблицю символів просто `add` — доведеться якось закодувати у символі всю інформацію: і ім'я функції, і типи її параметрів.

Цей процес кодування і називається **name mangling** — "спотворення імені". Компілятор бере ім'я функції, типи її аргументів, простір імен у якому вона живе — і перетворює все це на один рядок, який стає символом у таблиці.

### Як виглядає mangled-символ

Конкретний алгоритм залежить від компілятора, але GCC і Clang на Linux дотримуються Itanium ABI — відкритого стандарту. Результат виглядає приблизно так: функція `add(int, int)` у глобальному просторі імен стає символом `_Z3addii`. Розшифрувати можна так: `_Z` — маркер C++-символу, `3` — довжина імені "add", `add` — власне ім'я, `ii` — два аргументи типу `int` (i = int).

Якщо функція живе у просторі імен `math`, символ стане `_ZN4math3addEii` — тут додається `N...E` для вказівки namespace і `4math` (довжина 4, ім'я "math"). Метод класу `Calculator::add` дасть ще довший рядок — туди закодується і клас, і метод, і аргументи.

На Windows MSVC використовує інший алгоритм mangling — він несумісний з Itanium ABI. Символ тієї ж функції виглядатиме зовсім інакше. Це одна з причин, чому `.lib`-файли, зібрані MSVC, не можна просто так злінкувати з кодом, скомпільованим Clang на Windows без додаткових зусиль.

### Практичний наслідок: звідки береться "undefined reference"

Уявіть типову ситуацію: у вас є C++-функція `int add(int a, int b)` у файлі `math.cpp`. Ви хочете викликати її з ASM-коду і оголошуєте у ASM символ `add`. Компілюєте обидва файли — і отримуєте "undefined reference to `add`". Чому?

Тому що у `math.o` функція лежить не під ім'ям `add`, а під ім'ям `_Z3addii`. ASM-файл шукає символ `add` — якого не існує. Лінкер чесно каже: не знайшов.

Ця ж проблема виникає у зворотному напрямку: якщо C-код намагається викликати C++-функцію, яку не обгорнули у `extern "C"`. Заголовковий файл каже `int add(int, int)`, але реальний символ у `.o` — `_Z3addii`, і лінкер знову не знаходить збігу.

### `extern "C"` — міст між мовами

Рішення цієї проблеми — директива `extern "C"`. Вона каже компілятору C++: цей символ треба покласти у таблицю без mangling, рівно так само як це зробив би C-компілятор.

```cpp
extern "C" int add(int a, int b);       // оголошення
extern "C" int add(int a, int b) { ... } // визначення
```

Після цього символ у таблиці буде просто `add` — і ASM, і C, і будь-який інший код знайде його без проблем.

Для бібліотек, які мусять бути доступні як з C, так і з C++, є усталена ідіома з препроцесорним макросом:

```c
#ifdef __cplusplus
extern "C" {
#endif

int add(int a, int b);
void reset(void);

#ifdef __cplusplus
}
#endif
```

Коли цей заголовок підключає C++-код — він бачить `extern "C" { ... }` і розуміє, що символи всередині без mangling. Коли його підключає C-код — `__cplusplus` не визначений, і `extern "C"` просто ігнорується, бо C його не розуміє. Це стандартний спосіб написати заголовок, сумісний з обома мовами — і він зустрічається у кожній C-бібліотеці, яка розрахована на використання з C++.

Важлива обмеженість: `extern "C"` знімає mangling, але **не знімає перевантаження**. Не можна оголосити дві функції `extern "C"` з однаковим ім'ям і різними типами аргументів — символи будуть однаковими і лінкер не розрізнить їх.

### Demangle: як читати mangled-імена

Коли `nm` або `readelf` виводять таблицю символів C++-об'єктника, ви бачите сирі mangled-рядки: `_ZN10Calculator3addEii`, `_ZNK10Calculator6resultEv` тощо. Читати це очима — боляче.

Для цього є інструмент `c++filt` — він приймає mangled-ім'я і повертає читабельну форму:

```
c++filt _ZN10Calculator3addEii
→ Calculator::add(int, int)

c++filt _ZNK10Calculator6resultEv
→ Calculator::result() const
```

Прапор `-C` у команди `nm` робить те саме автоматично — `nm -C` одразу виводить demangle-d символи. Це перше, що варто зробити коли дебажите C++-бінарник через таблицю символів.

### Name mangling в інших мовах

C++ — не єдина мова, де є mangling. Rust теж змінює імена символів: функція `add` у модулі `math` у крейті `mylib` може отримати символ на зразок `_ZN5mylib4math3add17h8a3f2c1e4d5b6789E` — де в кінці є хеш, унікальний для конкретної версії компіляції. Це зроблено навмисно: Rust не гарантує стабільний ABI між версіями, і хеш захищає від випадкового злінкування несумісних версій однієї бібліотеки.

Тому в Rust, коли потрібно зробити функцію доступною для C або ASM, використовують атрибут `#[no_mangle]` — прямий аналог `extern "C"` в сенсі "не спотворюй ім'я". Разом з `extern "C"` в оголошенні це дає символ без жодних перетворень.

Swift, D, Fortran — у кожної мови свій алгоритм mangling. Але загальний принцип однаковий: C — єдина мова, де символи залишаються незайманими. Саме тому `extern "C"` — це не просто директива для C++, а універсальний "роз'єм" для підключення будь-якої мови до будь-якої іншої через спільний C ABI.

### Підсумок

Name mangling — це не примха компіляторів, а технічна необхідність для мов із перевантаженням і просторами імен. Розуміння цього механізму пояснює цілий клас загадкових помилок лінкування і дає інструмент для їх вирішення: `extern "C"` там де потрібна C-сумісність, `c++filt` і `nm -C` там де потрібно читати що реально лежить у бінарнику.

## 6. ASM ↔ C: виклики між мовами (~17 хв)

Тепер у нас є всі складові: ми знаємо як влаштовані об'єктні файли, як лінкер знаходить символи, як передаються аргументи і як не заплутатись з іменами. Час зібрати це разом і написати реальний код, де C і ASM розмовляють одне з одним.

Є три режими цієї взаємодії. Перший — C викликає функцію, написану на ASM. Другий — ASM-код викликає C-функцію. Третій — ASM вбудований прямо всередину C-файлу через спеціальний синтаксис. Кожен режим має свої правила і свої типові помилки.

### Режим 1: C викликає ASM-функцію

Це найпростіший і найпоширеніший сценарій. Ви пишете функцію на асемблері, яка реалізує щось, чого не може або не хоче генерувати компілятор, а C-код викликає її як звичайну функцію.

З боку C все виглядає тривіально: потрібно оголосити прототип функції зі словом `extern`, щоб компілятор знав її сигнатуру, але не шукав визначення у C-файлах:

```c
extern int add(int a, int b);

int main(void) {
    int result = add(3, 4);  // викликаємо як звичайну функцію
}
```

З боку ASM потрібно зробити кілька речей. Перше — оголосити символ глобальним, щоб лінкер його бачив: `global add`. Без цього символ залишиться локальним у об'єктному файлі і лінкер не знайде його. Друге — реалізувати функцію, дотримуючись calling convention: перший аргумент прийде у `rdi`, другий у `rsi`, результат треба покласти у `rax` і виконати `ret`.

```nasm
section .text
global add

add:
    mov eax, edi      ; перший аргумент (int — 32 біти)
    add eax, esi      ; додаємо другий аргумент
    ret               ; результат вже у eax/rax
```

Зверніть на деталь: аргументи типу `int` — 32-бітні, тому беремо `edi` і `esi`, а не `rdi` і `rsi`. Результат також 32-бітний, але `mov eax, edi` автоматично обнуляє верхні 32 біти `rax` — це гарантія архітектури x86-64. Тому `rax` буде коректним 64-бітним поверненням навіть якщо ми писали у `eax`.

Компілюємо і лінкуємо:
```bash
nasm -f elf64 add.asm -o add.o
gcc main.c add.o -o program
```

Ось і все. З точки зору C-коду `add` — звичайна функція, і він не знає і не піклується, що вона написана на ASM.

**Типові помилки.** Забути `global` — лінкер скаже "undefined reference". Використати 64-бітні регістри для 32-бітних аргументів — формально не помилка, але якщо у верхніх 32 бітах `rdi` є сміття, результат буде неправильним. Не повернути значення у `rax` — caller прочитає що завгодно.

### Режим 2: ASM викликає C-функцію

Зворотний напрямок — ASM-код хоче скористатись готовою C-функцією. Найбільш показовий приклад — виклик `printf`, тому що він добре ілюструє всі тонкощі.

З боку ASM потрібно оголосити символ як зовнішній: `extern printf`. Лінкер потім знайде його у `libc`. Далі — підготувати аргументи згідно з calling convention і зробити `call printf`.

```nasm
section .data
    fmt db "Result: %d", 10, 0   ; рядок формату, 10 = '\n', 0 = null-terminator

section .text
extern printf
global main

main:
    push rbp                  ; зберігаємо базовий вказівник
    mov rbp, rsp              ; встановлюємо фрейм

    lea rdi, [rel fmt]        ; перший аргумент: вказівник на рядок формату
    mov esi, 42               ; другий аргумент: число для %d
    xor eax, eax              ; кількість xmm-аргументів = 0 (variadic convention)
    call printf

    xor eax, eax              ; повертаємо 0 з main
    pop rbp
    ret
```

Тут є кілька важливих деталей, які новачки пропускають.

**`xor eax, eax` перед `call printf`.** `printf` — variadic функція (приймає змінну кількість аргументів). За System V ABI, при виклику variadic функцій значення `al` (молодший байт `rax`) має містити кількість аргументів, переданих через `xmm`-регістри. Якщо в `al` випадково виявиться ненульове число — `printf` вирішить, що є векторні аргументи і спробує їх прочитати з `xmm0`, `xmm1` тощо, де лежить сміття. Результат — або неправильний вивід, або падіння.

**Вирівнювання стека.** Перед `call printf` стек мусить бути вирівняний на 16 байт. При вході у `main` стек вже зміщений на 8 байт через `call` з попереднього рівня. `push rbp` додає ще 8 — разом 16, вирівнювання відновлено. Якщо між `push rbp` і `call printf` є ще `push`-и, треба рахувати: непарна кількість `push`-ів після `push rbp` зламає вирівнювання.

**`lea rdi, [rel fmt]`.** Для завантаження адреси рядка у Position Independent Code (PIE) треба використовувати RIP-відносну адресацію через `rel`. Без `rel` у деяких конфігураціях лінкер видасть попередження або помилку.

**Збереження регістрів.** Якщо у вашому ASM-коді до виклику `printf` у `rbx` зберігається важливе значення — не треба нічого робити: `rbx` є callee-saved, тобто `printf` зобов'язана його зберегти і відновити. Але якщо важливе значення лежить у `r10` або `r11` — вони caller-saved, і `printf` може їх знищити. Зберігайте перед `call`, відновлюйте після.

### Режим 3: Inline Assembly у C

Іноді писати окремий ASM-файл надмірно. Для вставки кількох інструкцій прямо у C-код GCC і Clang підтримують синтаксис **extended inline asm**:

```c
int result;
int a = 10, b = 20;

__asm__ volatile (
    "addl %2, %1\n\t"
    "movl %1, %0"
    : "=r"(result)        // output: result ← будь-який регістр
    : "r"(a), "r"(b)      // input:  a і b у регістрах
    : // clobbers: нічого не псуємо додатково
);
```

Перша секція після першого двокрапки — **outputs**: які C-змінні отримають результат і через яку обмежувальну букву (`=r` — запис у будь-який регістр). Друга секція — **inputs**: які змінні подаємо на вхід. Третя — **clobbers**: список регістрів або пам'яті, які ASM-вставка може зіпсувати, але не декларує як outputs. Якщо забути вказати регістр у clobbers, компілятор може не врятувати його перед вставкою і значення зникне.

Слово `volatile` забороняє компілятору переміщувати або видаляти цю вставку. Без нього оптимізатор може вирішити, що вставка не має side effects і викинути її.

**Де inline asm доречний, а де ні.** Доречний — для одиничних привілейованих інструкцій: `cpuid`, `rdtsc`, `pause`, порти вводу-виводу. Доречний — для атомарних операцій і memory fence інструкцій, хоча сучасний C11 `_Atomic` і `stdatomic.h` часто кращий вибір. Недоречний — для великих блоків оптимізованого коду: набагато зручніше і надійніше винести у окремий `.asm`-файл, де весь контекст зрозумілий. Недоречний також якщо той самий ефект можна досягти через intrinsics — спеціальні C-функції, які компілятор перетворює у конкретні інструкції без ризику помилки у clobbers.

### Загальна схема: що тримати в голові завжди

Незалежно від напрямку виклику, є три речі, які треба перевіряти щоразу:

Перше — **символи**. ASM-функція, яку викликає C, мусить бути `global`. C-функція, яку викликає ASM, мусить бути `extern` у ASM-файлі. Якщо C++ — треба `extern "C"` щоб уникнути name mangling.

Друге — **calling convention**. Аргументи у правильних регістрах, результат у `rax`, callee-saved регістри збережені якщо ви їх використовуєте.

Третє — **вирівнювання стека**. Перед кожним `call` стек вирівняний на 16. Рахуйте `push`-и, враховуйте `call` який кладе return address.

Якщо всі три пункти виконані — код працює. Якщо щось іде не так — майже завжди проблема в одному з трьох.

## 7. Interop з іншими мовами (~19 хв)

Ми детально розібрали взаємодію ASM і C. Але C — це не кінцева мета, а прошарок. Реальні системи пишуть на Python, Rust, Go, Java, C++ — і всі вони рано чи пізно хочуть скористатись або бібліотекою на C, або прискорити критичну ділянку кодом на нижчому рівні. Механізм скрізь один і той самий: C як спільна мова-посередник з відомим, стабільним ABI. Подивимось як це виглядає у кожній з популярних мов.

### C++ ↔ C: найближчі сусіди

C++ і C здаються майже однаковими, але у контексті лінкування між ними є один принципіальний бар'єр — name mangling, про який ми вже говорили. Нагадаємо суть: компілятор C++ кодує у символ не лише ім'я функції, а й типи її аргументів. C-компілятор цього не робить. Тому якщо C хоче викликати C++-функцію без додаткових вказівок — лінкер не знайде символ.

Рішення — `extern "C"` на стороні C++-коду. Але проблема складніша ніж просто додати ключове слово. Якщо ви пишете бібліотеку на C++, яку мають використовувати і C-, і C++-клієнти, вам потрібен заголовковий файл, який коректно компілюється в обох контекстах. Стандартна ідіома виглядає так: у заголовку весь публічний інтерфейс обгортається у блок `#ifdef __cplusplus / extern "C" / #endif`. Коли заголовок підключає C++ — блок активний і символи кладуться без mangling. Коли підключає C — блок ігнорується, бо C не розуміє `extern "C"` як конструкцію мови, але сприймає його коректно.

Є також зворотна задача: викликати C-бібліотеку з C++. Тут все простіше — якщо підключати C-заголовок у C++-коді без `extern "C"`, компілятор спробує застосувати mangling до імен, яких немає у бібліотеці. Правильно: або обгорнути `#include <foo.h>` у `extern "C" { ... }`, або переконатись, що сам заголовок вже містить захисний блок.

Важлива обмеженість: `extern "C"` не дає перевантаження. Не можна мати дві `extern "C"` функції з однаковим ім'ям і різними аргументами — символи злиплись б. Тому публічний C-сумісний інтерфейс бібліотеки завжди має унікальні імена функцій, часто з префіксом: `mylib_init`, `mylib_process`, `mylib_free`.

### Rust FFI: безпека і небезпека поруч

Rust побудований навколо концепції безпеки пам'яті — і це одразу створює напругу при взаємодії з C, де ніяких гарантій немає. Тому Rust чесно каже: виклик зовнішнього C-коду — це `unsafe`. Не тому що C завжди небезпечний, а тому що компілятор Rust не може перевірити інваріанти на тому боці межі.

Щоб викликати C-функцію з Rust, її оголошують у блоці `extern "C"`:

```rust
extern "C" {
    fn add(a: i32, b: i32) -> i32;
}

fn main() {
    let result = unsafe { add(3, 4) };
}
```

Блок `extern "C"` каже Rust-компілятору: ці функції десь зовні, не шукай їх реалізацію тут. Виклик обгорнутий у `unsafe` — це явна позначка: "тут я виходжу за межі гарантій Rust, відповідальність на мені".

Зворотний напрямок — зробити Rust-функцію доступною для C. Для цього потрібні два атрибути разом. `#[no_mangle]` каже компілятору не змінювати ім'я символу — без нього Rust додасть свій унікальний хеш у кінці. `extern "C"` у оголошенні функції каже використовувати C calling convention замість Rust-власного:

```rust
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    a + b
}
```

Після компіляції у `.so` ця функція лежить під символом `add` і доступна будь-якому C-коду. Одна тонкість: типи мусять відповідати. `i32` у Rust відповідає `int32_t` у C. Для складніших типів — структур, вказівників — потрібна точна відповідність розмірів і вирівнювання, яку гарантує атрибут `#[repr(C)]` на структурах.

На практиці для великих FFI-інтерфейсів у Rust-спільноті є інструмент `bindgen`: він читає C-заголовковий файл і автоматично генерує Rust-оголошення для всіх функцій і типів. Це рятує від ручного прописування сотень прототипів і від помилок невідповідності.

### Python ctypes і cffi: динамічний міст

Python — інтерпретована мова з GC, і у неї немає фази лінкування. Але Python може завантажити `.so`-бібліотеку прямо під час виконання і викликати з неї C-функції. Для цього є два основних підходи.

**ctypes** — стандартна бібліотека, не потребує нічого встановлювати. Принцип: завантажити бібліотеку, описати сигнатуру функції (типи аргументів і результату), викликати:

```python
import ctypes

lib = ctypes.CDLL("./libmath.so")
lib.add.argtypes = [ctypes.c_int, ctypes.c_int]
lib.add.restype = ctypes.c_int

result = lib.add(3, 4)
```

Якщо не описати `argtypes` і `restype` — Python не знає типи і або передасть неправильні байти, або неправильно інтерпретує результат. Без `restype` за замовчуванням Python вважає, що функція повертає `int` — і це спрацює для `add`, але не для функцій що повертають `double` або вказівник.

**cffi** (C Foreign Function Interface) — більш потужний інструмент, популярний у PyPy і сучасних проектах. Він дозволяє передати прямо C-заголовок у вигляді рядка і cffi сам розбере типи:

```python
from cffi import FFI
ffi = FFI()
ffi.cdef("int add(int a, int b);")
lib = ffi.dlopen("./libmath.so")
result = lib.add(3, 4)
```

Це зручніше при великому інтерфейсі: можна скопіювати вміст заголовкового файлу і не описувати кожну функцію вручну.

Обидва підходи об'єднує одне: вони не вимагають жодних змін у C-бібліотеці. Бібліотека не знає, що її викликає Python, а не C. Вона отримує правильні аргументи у правильних місцях і повертає результат — і цього достатньо.

### Go cgo: вбудований міст

Go має вбудований механізм виклику C-коду — `cgo`. Він активується автоматично, якщо у Go-файлі є спеціальний коментар безпосередньо перед `import "C"`:

```go
/*
#include <stdlib.h>
int add(int a, int b);
*/
import "C"

func main() {
    result := C.add(3, 4)
}
```

Псевдопакет `C` дає доступ до C-функцій і типів. `C.int`, `C.char`, `C.malloc` — все це відповідники C-типів. Під капотом cgo генерує прошарок коду, який переводить Go calling convention у C calling convention, і навпаки.

Але cgo має репутацію "дорогого задоволення". Перехід між Go і C — це справжній перехід між двома рантаймами зі своїми стеками (Go використовує goroutine стеки, що ростуть динамічно, C — фіксований стек), зі своїм управлінням пам'яттю. Кожен виклик через cgo коштує значно більше, ніж звичайний Go-виклик. Тому в Go-спільноті є правило: якщо cgo — то для важких операцій, де вартість переходу незначна на фоні роботи всередині C-коду. Для дрібних викликів у циклі — краще переписати логіку на Go.

### Java JNI: найважчий варіант

Java Native Interface — механізм виклику C/C++ з Java (і навпаки). Він найскладніший з усіх розглянутих, тому що JVM вносить додатковий шар: об'єкти Java живуть у heap під управлінням GC, і при передачі їх у C-код треба обережно керувати посиланнями, щоб GC не прибрав об'єкт поки C-код ще ним користується.

Щоб викликати C-функцію з Java, треба оголосити `native`-метод у Java-класі, скомпілювати клас, згенерувати C-заголовок утилітою `javah` (або `javac -h`), реалізувати функцію у C з точно заданим ім'ям і сигнатурою, і завантажити `.so` через `System.loadLibrary`. Ім'я C-функції має відповідати шаблону `Java_пакет_клас_метод`, інакше JVM не знайде її.

Через складність і накладні витрати JNI використовують рідко і точково — там де реально немає альтернативи: доступ до апаратного API, інтеграція з легасі-бібліотеками, критичні числові ядра. Більшість Java-розробників за кар'єру майже не торкаються JNI напряму — але розуміти що він існує і як влаштований корисно.

### Спільний знаменник

Попри різні синтаксиси і механізми, всі ці підходи реалізують одну ідею. Кожна мова будує свій тонкий міст до C ABI: описує типи, узгоджує calling convention, передає управління. C-бібліотека нічого про це не знає — вона просто отримує аргументи і повертає результат за правилами, які не змінились з 1970-х. Саме ця незмінність C ABI і робить його таким цінним: написавши бібліотеку на C один раз, ви отримуєте доступ до екосистеми будь-якої мови, яка вміє з ним говорити.
